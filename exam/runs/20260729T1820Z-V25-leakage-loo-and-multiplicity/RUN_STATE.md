### B1 · token 普查（`b1_token_census.py` → `token_census.json`）

对四份出厂卷子加 `handover_auto`，逐 (卷子 / 标签集 / kind 组 / 字段 / token) 列出
n、k、闸门统计量、组底线、以及**在超几何零假设下精确枚举**的 p 值
（不抽样、不用随机数——组够小就该枚举，抽样会把种子写进制品、把容差写进每条下游测试）。

```
tokens enumerated             261
scored by the shipped gate     24     <- 9.2%
single-holder (k=1, unscored) 237     <- 90.8%
fires today                     0
被打分的组：n = 6, 7, 8, 11, 12, 80
每(组,字段)被打分的 token 数：m = 2 或 3，**max m = 3**
真卷子上最显著的被打分 token：p = 0.5636（handover/tags `yard`，n=11 k=2）
```

**两条数把工单的第二半改写了。**

  这句话必须随校正一起发表，否则读者会以为它修好了什么。

### B2 · 三种判据对同一批夹具（`b2_three_rules_on_fixtures.py`）

四个夹具，两个必须响、两个必须不响。第四个是**决定性的那个**：
M5_ID —— 把 M5 里的真泄漏 token `ridge` 换成纯逐件标识符 `tag07`，**位置一模一样**。

```
case                                   gate    loo     exact
DIRTY (V21 负控 1，真 token 泄漏)       True    True    True     <- 都对
CLEAN (V21 负控 2，干净)                False   False   False    <- 都对
M5    (真的单持有者泄漏)                False   False   False    <- 都漏
M5_ID (同一件上的标识符)                False   False   False    <- 都对
```

M5 与 M5_ID 的三组数**逐字相同**：`gate` 都被 k=1 守卫挡住；
`loo` 都是 acc=0.9167、base=0.9167（差 0，离 0.25 的 margin 差得远）；
`exact` 都是 p=0.083333。

### 由此得到的裁定（这是本条最重要的产出）

**工单第一半的前提是错的。** 它写着「正路在 `a12_independent_audit.py` 里已经跑通了一个原型」，
而 `a12` 的留一法框架**同样治不了 M5**——它的 acc 与 base 精确相等。
原因不是参数没调好，是这类判据够不着：

> 一个只落在一件上的 token，它的全部统计量都只是**「它落在哪一件」的函数**，
> 与这个 token 是什么无关。所以对任何只读 (carrier 集合, 标签) 的判据 R，
> 必然 R(`ridge`) = R(`tag07`)。而 `tag07` 是标识符、**必须不响**，
> 于是 R 在 `ridge` 上也必然不响。

这不是测出来的巧合，是可证的。`a12` 的留一法把弃答记成答错，正是为了让标识符得 0 分——
那个机制работает得很好，但它同时抹掉了真泄漏，因为留一法留掉的正好是唯一携带信息的那一件。

**所以 M5 不是「守卫没放宽」，守卫是结论不是原因。** 能够着 M5 的只有跳出这个框架的东西：
token 的**表面形态/语义**（`ridge` 像内容词、`tag07` 像编号），或者**外部声明**
（check 1 的 `leak_probes`——出题人自己说什么会泄露答案）。前者是猜，后者已经在闸门里了。

## 精确不能靠不完的时间买（cycle 72，B4）

上一世把「精确枚举」当成对 V21 抽样零假设的改进就收工了。这一世第一件事是量它的代价，
**量出来它是指数级的，而指数在我们控制不了的那一维上**：

`_fire_count_bruteforce` 走遍 carriers 在各答案类之间的每一种分法，共 ∏(sᵢ+1) 种，
指数在**答案类的个数**上。而答案类的个数由考卷的答案决定，不由闸门决定——
一份答案是整数的卷子（`plan_len`）有多少个不同答案就有多少类。本机实测：

```
2 类 n=80    0.00s
4 类 n=80    0.01s
6 类 n=80    0.46s      <- 出厂卷子里最大的真实分组就在这
8 类 n=80   14.67s      <- 每加两类 ×30
12 类 n=120 跑不完
```

**一个慢到会被关掉的闸门等于不存在的闸门**——这正是本赛道存在的理由，
所以这不是性能优化，是这条检查能不能上线的前提。

改法：判据只看两个量（最大的 carrier 类、最大的非 carrier 类），
分法本身无关。于是逐类推进 `(taken, max_with, max_without)` 三元状态，
并把「最乐观的补全也点不着」的状态就地丢掉（`_fire_count`）。
`_fires` 这个谓词被计数器与神谕**共用**，所以两者不可能各自漂移到不同阈值上去——
一个按别的阈值算出来的假阳性率比没有率更糟，因为它长得像一次标定。

代价换掉了，答案没换掉，这一点是**证的不是说的**（`b4_fast_count_vs_oracle.py`
→ `fast_count_check.json`）：

* 差分扫描 **2130 个组态**（n≤9、≤4 类、每个 k、六个容差，含 0.875——它正好是 7/8，
  n=8 时是一次精确浮点相等，重写就是在这种地方悄悄跑偏的；也含 0.50，
  此时是多数类底线而不是容差在管事）：**0 处不一致**；
* 光在 0 上一致是白送的，所以另有大计数用例：`(40,30,4,3,2,1)` k=35
  两边都给 **64222354820657532200**；`(75,1,1,1,1,1)` k=3 两边都给 10 = C(5,3)；
* 从前病态的那几档现在都是 0.0000s，20 类 n=200 也是。

出厂卷子上四份的 p_fire 一个数没动（`check_paper` 整套从 1.10s 降到可忽略）。
测试里钉了三条：`test_the_fast_count_agrees_with_the_oracle_everywhere`（缩小版差分扫描，
0.02s）、`test_the_exact_count_survives_many_answer_classes`（20 类 n=200 有界时间内返回，
且在能开火的规模上仍然精确）、`test_an_empty_answer_class_changes_nothing`
（声明了却没人用的标签不该改变已公布的假阳性率）。

神谕留在模块里而不是删掉：`_fire_count` 的剪枝是全文件唯一不显然的一步，
它可信只因为有个显然正确的东西在它能跑的地方处处同意它。

## 对抗复核推翻了本条的核心裁定（cycle 74，最重要的一节）

派出去打「单持有者不可闭合」这条裁定的 subagent **推翻了它**，而且是带着可执行的
反例来的。我自己复核过它的每一个数，然后接受：**上一世的证明是对的，从证明里推出的
结论是错的。**

* 证明说的是：只读**一个 token 的持有者集合**的规则，必然对 `ridge` 与 `tag07`
  给出同一个答案。这一条是对的，`b2_three_rules_on_fixtures.py` 那三种判据都在这个
  量词范围内，所以它们当然一致。
* 但 `_token_hits_within` 手里有的不是一个 token 的持有者集合，是**整个字段的
  carrier map**。那是严格更多的信息，而它把这一对分得开：
  **一个字段里只有一个私有 token 是异常，十二个是编号。**

于是判据从「逐 token 问」改成**按字段问一次**：*在这个字段里携带私有标记，
能不能预测答案？* 一条切分、一次检验，而两种情形靠算术落在它的两边：

* 真泄漏只标记少数几件 → k < n，可打分，预测得准就红；
* 编号族标记每一件 → k == n，被**原本就在的常量守卫**丢掉，因为枚举什么也不预测。

`b5_pooled_private_cut.py` 把三种情形都跑了：M5（真泄漏）红、M5_ID（编号族）不响、
M5_EVADE（每件都塞一个诱饵私有标记，把 k 推到 n）不响——**最后一条是已知的规避手法，
写下来而不是掩掉**；能扛住它的判据（按字段众数私有标记数取偏离）也量了，但**不在本条上线**：
那是第二个设计决定，本条存在的理由就是两个决定塞一个 diff 里事后分不清。

### 打快速计数器的那个：117 万个组态零不一致，但抓到三条真缺陷

它自己另写了一个独立的逐 k-子集枚举器，用**三方**（快速／仓库神谕／它自己）比对，
所以连我的神谕也被验了一遍。零不一致。但它找到的三条都是真的，都已修：

1. **`_fires` 的承诺是「抄一遍」不是「调一次」。** 它的 docstring 写着计数器与闸门
   共用这个谓词所以「不可能漂移」，而 `_token_hits_within` 当时把比较**内联抄了一遍**。
   它对 `_fires` 做变异测试：`>=` 换 `>`、以及去掉 `1e-9`，**两个都活过了这一带全部 66 条测试**——
   因为计数器和它的神谕都走 `_fires`，会一起动，所以「快速与神谕一致」这条测试
   结构上看不见这种漂移。而 `>=` 那个不是学术问题：**9/10、18/20、36/40、72/80
   全都正好等于双精度的 0.90**，所以容差就坐在一个可达的平局上，
   包括 n=80 这个最大的真实分组；在那个变异体下 p_fire 从 0.0 变成 10/210，
   而闸门仍然不开火——**公布一个闸门不按它开火的假阳性率**，正是 `_fires` 自己
   docstring 里说「比没有率更糟」的那件事。已改成真的调用 `_fires`，
   并加 `test_the_published_rate_and_the_gate_agree_on_the_exact_tie` 钉死
   （已验证该测试确实杀掉 `>=` 变异体）。
   去掉 `1e-9` 那个变异体**杀不掉，而且不该杀**：`best` 是整数、`floor` 是同分母的
   `max(sizes)/n`，所以在 `_fires` 里两者等价（它测了 7548 个组态，计数一次没变）；
   那点余量只在整值那条路上真的承重（比率按被打分子集算、底线按全组算，分母不同）。
   这句话写进了 `_fires`，省得下一个跑变异报告的人去找一条不可能存在的测试。
2. **`group_power` 漏了 k=1。** 我按「单持有者 token 从不被打分」把扫描起点设在 2，
   但那句话是对 **token** 成立、对**这项检查**不成立：池化切分可以只握一件，
   M5 上它就是 k=1 而且开火。于是我低估了这个函数存在的意义所在的那些分组。已改成 1..n-1。
3. **`group_power` 没有 memo、也没用互补对称。** 它每个分组每个标签集调一次、
   内部扫遍每个 k，n 几百时单次 1.6–6.5 秒、乘四个标签集到 26 秒。
   已加 `lru_cache`（键是排序后的类大小——类名不影响答案）并只扫到 n//2
   （`p(k) == p(n-k)`，互补把两个极大值对调而谓词只读它们的和）。
   顺带把那条对称性也钉成测试：`cuts.setdefault` 保留的是**排序在前**的那个 token 的 p，
   所以公布的族错误率只有在对称成立时才与 token 拼写无关——否则又变成
   「精确计数要消灭的那种东西」。它量了 45470 对，零不对称。
4. 还修了它指出的一处印法：`best_p_fire` 用 `round(x, 6)` 会把 1.5e-27 印成 `0.0`，
   而**真的不可能**那种情形印的是 `None`——两种情形印得不一样才有意义，
   现在改成六位**有效数字**。

### 打读者可见性的那个：`group_power` 当时是死代码

这一条最难看，因为它就是 V21 那族缺陷在**我自己的修正里**的第三次复现：

* **`group_power` 零调用者、零测试。** 它的 docstring 亲口说「`ALPHA` 承诺了
  过小的分组要记成 untestable，没人算，所以那个承诺只是散文」——然后它自己也没人调。
  已接进 `check_paper`。
* **干净卷子上乘数校正一个字都不发布**：那些键只挂在 finding 上，而出厂四份全都没有 finding。
  已改成 `check_paper` 逐标签集发布 `metadata_multiplicity`（有没有 finding 都发）。
* **覆盖率记录被 `if coverage["single_holder"]:` 挡住**——于是「打分了 3 个、一个没跳过」
  这种好消息永远不说，而这正是它上面三行的注释明令禁止的事；
  出厂四份里有**两份**因此一条 token 覆盖率记录都没有。已改成无条件发布。
* 它另外指出 `scored_values: 0` 与整值检查的同名键撞车（读者求和会少算），已改名 `scored_tokens`。
* 以及闸门抛错时 `findings[:8]` 会把元数据 finding 整个截掉（探针 finding 排在前面），
  **恰好在把人叫来裁决的那一刻把「这条红值多少」丢掉**。已改成两类各切一半，
  并把 `findings`／`multiplicity`／`metadata_unscored` 作为属性挂到异常上。

**这一段的元教训**：三个 subagent 里有两个是在打我这一轮**刚写的东西**，
两个都在里面找到了 V21 同一族缺陷的新实例。所以「派对抗性复核」不是仪式——
本条如果不派，会带着一个死函数、一个只在脏卷子上说话的校正、
和一个抄错就没人知道的阈值交付。

## 顺手量到、**故意没在本条治**的一件（cycle 72）

重建制品时发现：本分支 `exam/artifacts/papers/*.paper.json` 里的 `rubric_digest`
是 `e06bdf52…`，而本分支源码现在算出来是 `63ce1eab…`——**分支上committed的考卷携带着
一个重建复现不出来的摘要**。查清楚了原因与范围，两条都要写下来：

* **master 上没有这个问题**（`36a23877…` 两边相等，已用 `git show` 逐模块核对）。
  本分支的错位只是滞后：V21 基于一个 `exam/artifacts` 尚未随 `18a39417`
  （改了打分模块）重建的 master。所以这不是 master 的缺陷，不需要事故记录。
* 但它暴露了一个**闸门缺口**：`exam/verify.py` 跑 `build_papers`，而 `build_papers`
  是**覆写**制品的——它把证据本身覆盖掉了，所以「committed 的制品与源码重建不一致」
  这一类漂移在 verify 全绿的情况下可以一直存在，本分支就是一个活实例。
  另一半是 `build_manifest.json` 里存着**构建时的绝对路径**
  （旧值指向 `.worktrees/v4-exam-selftest`），所以那个文件永远不可能逐字节匹配，
  修缺口之前得先把它相对化。

这一条**已经在板上**：`monitor/board/items/V2-V25-verify-does-not-check-what-is-committed.md`
（上一世 cycle 71 立的，同样的两个摘要、同样的绝对路径半边都在里面）。
本轮唯一的新料是把那条工单的第 2 步（「先判定当前漂移是哪一种」）答了：
**是签入的制品陈旧，不是 rubric 被误改**——`master` 上 registry 重算与卷子上的摘要

所以那条工单该做的是重建并提交，不是回退 rubric。已把这句追加进工单，
