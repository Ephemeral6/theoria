# Agent 舰队 —— 搁置中的第二篇论文

**状态：构思暂缓，证据采集照常。** 主线（Theoria 论文）做完之后再动笔。
本文件是这个 idea 的存放处，写给那时候的我们，也写给中途接手的任何人。

## 主张（用户 2026-07-28 定的，不要在写作时把它缩小）

> **AI 的使用单位正在从「会话」变成「舰队」。一个人配备一支持续运转、
> 自我组装、自我审计的 agent 编队，是可行的——这可能改变 AI 的使用方式。**

会话是一次性的、要人守着的，能力上限等于单个模型的上下文。
舰队是持续的、自我供货的，能力上限等于**组织结构**。
差别不是量的（agent 多几个），是质的：**当组装权本身交给 agent 之后，
人的角色从操作员变成下达意图的人。**

## 这篇文章要提供的是可能性，不是无可挑剔的论证

用户的原话：「这篇文章不是要让这个概念无可挑剔，而是提供了一个全新的可能性。」

成功标准是**读者读完想去试**。它靠的是**存在性证明**——这东西真的跑起来了、
产出了真东西、你也可以建一个。它不声称最优，只声称这条路存在。

**n=1、一天、无对照组：不解释、不辩护。** 存在性证明只需要一个。把它写成
「局限性」反而是在暗示它本该有更多。

## 监控自己犯过的两次错，留作提醒

写作时最可能重犯的偏向，是**把主张缩到容易被辩护的尺寸**。今天犯了两次：

1. 第一次把它降级成「经验报告」——退守到「这是我们撞到的坑和怎么补的」，
   安全，但读者读完不会改变任何行为；
2. 第二次升级成「有边界的概念论文」——加了四个必要条件、排除法、代价清单。
   看起来更严谨，其实仍是防守：**定义边界等于告诉读者哪些事不该试**，
   而提供可能性的文章应该让人觉得**还有很多没被试过**。

用户两次都指出来了。写作时若又想加「适用边界」一节，先回来读这一段。

## 骨架（航海日志，不是规格说明）

核心不是架构图，是**「看，这东西真的在运转」**，以及**它是怎么长出来的**——
不是设计出来的，是被一次次事故逼出来的：

* 邮箱延迟十二小时 → 逼出总线（带回执与打断）；
* 账本被并发污染 → 逼出花钱串行化（只有一个 agent 能花 API 钱）；
* 八个活着的工人被报成已停 → 逼出编码校正与「探针必须能自检」；
* 死工人的认领永不释放、板替死人占着领地 → 逼出自动清扫；
* 逐件派单不可扩展 → 逼出自助工作板；
* 分不清「闲着」与「掉线」 → 逼出统一心跳；
* 闸门是自觉条款 → 逼出机器检查。

这个「被逼出来」的过程比任何架构图都有说服力，因为它告诉读者：
**你不需要一开始就想清楚，可以边跑边长。** 这本身就是可能性的一部分。

失败照写，但**写成航行中的天气，不是局限性章节**——它们让日志可信，
让读者知道会遇到什么，但不用来划定「这条路只能走到这里」。

## 悬而未决的一个问题（动笔前先定）

**读者读完的第一反应，你要的是哪个？**

* 「我也要建一支」→ 重心在可复制的细节，`fleetkit` 是核心交付物甚至主角；
* 「原来 AI 可以这么用」→ 重心在意味着什么，fleetkit 退为附录，正文讲人的角色变了。

监控的倾向是前者（可验证的行动 > 容易变空话的感受），但**这个由用户定**。

## 现在就做、以后补不回来的

**证据会腐烂——数字还在，但「当时为什么这么判」随会话上下文蒸发。**
所以采集不暂缓，且不应停在今天：

* `S17-fleet-evidence-capture` 转为**常设日志**，每天追加，而不是一次性快照。
  跑够两三周再动笔，那时手上的是「一支舰队的连续运转记录」，
  而不是「一天的快照」——可能性的说服力强得多。
* **人类动作账**是唯一会随时间永久损失的数据：每次人出手就记一条
  （时间、动作、为什么它不能自动化）。组装权下放的价值 = 这张表有多短。
* **反例清单**同等重要：装了却没用上的机制、担心过却从未发生的失败。
  没有这一栏，任何系统记录都会滑向事后合理化。
