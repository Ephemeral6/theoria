## 0. 怎么读这份记录

四条纪律，写在最前面，因为它们决定了哪些数字可以信：

1. **每一行都能被打开。** `data/*.jsonl` 的每一行都带 `evidence`，形如
   `git:<sha>` 或 `file:<path>`；`verify.py` 会逐条解析——sha 必须
   `git cat-file -t` 得到 commit，路径必须存在于工作树或 git 历史。
   引用一个从未存在过的东西，本身就是本记录里的一个失败类
   （`requirement_cites_nonexistent`，5 例）。
2. **校验器必须能变红。** `verify.py --selftest` 注入 11 个人造缺陷，
   断言它逐个拒绝。理由写在脚本开头：本数据集里有一类叫
   `check_with_no_failing_path`（检查没有失败路径，3 例）——
   一个不会变红的校验器就是同一个缺陷，只是高了一层。
3. **系统的自我描述不是测量。** 契约声称「改一个文件全队下轮生效」是**主张**；
   证据是日志里另一个已在运行的 agent 的行为真的变了。二者不可互换，
   本记录中凡是只有前者的，一律标 `confidence: low` 并写明它不能证明什么。
4. **没发生的事同样是证据。** `counterevidence.jsonl` 与失败清单同等重要：
   装了没用上的机制、担心过却从未发生的失败、以及**被抓住的过度声称**。
   没有这一栏，任何系统记录都会滑向事后合理化。

## 2. 架构不是设计出来的，是被事故挤出来的

`timeline.jsonl` 记 45 次架构变更，从 `2026-07-27T18:13Z`（监控层诞生，
一个只读看板）到 `2026-07-28T15:06Z`（舰队补满 12 席）——**约 21 小时**。

按触发原因分：`friction` 22、`incident` 15、`design` 5、`user_request` 3。

**「45 次里只有 5 次是设计出来的」这个读数不成立，已被对抗性复核推翻**
（C-46，详见 §6）。原因是 `friction` 是个残差桶：T-02 自己写着「提交信息未点名
具体事故，**因此归为 friction**」——没有点名事故就是归入 friction 的规则。
机器可查的后果是 **22 行 friction 里，0 行在 `evidence` 中引用任何 `F-nn` 或
`INC-` 事故**（整个 45 行表都是 0）；它们引用的全是**被造出来的那个产物**，
证的是结果，从不证原因。而且结论早于数据：IDEA.md 在采集之前就写好了
「不是设计出来的，是被一次次事故逼出来的」和一张七条的清单。

**没有被推翻的是下面这张表。** 逐条读 timeline，多数行的事故叙事确有具体痕迹
支撑；塌掉的是那个 5:37 的**比例**，不是「架构由事故塑形」这件事本身。

被逼出来的链条，每一环都能在 `timeline.jsonl` 里查到触发它的那次事故：

| 事故 | 逼出的机制 | 时刻 |
|---|---|---|
| 逐件派单不可扩展 | 工作板 `board.py`：原子领取、领地互斥、deps 门 | T-20, 04:03Z |
| 从监控自己的 shell spawn 出来的东西活不下来 | 每 agent 一个一次性计划任务，提示词走 stdin | T-19, 03:49Z |
| 长契约靠人粘贴，改一次要重贴全队 | 契约落盘 `monitor/ops/<ID>.md`，每周期重读 | T-23, 06:12Z |

| 死工人的认领永不释放，板替死人占着领地 | 板 sweep，反射层每 tick 跑一次 | T-37, 13:48Z |

这一栏的准确含义正在复核（§6）。

## 3. 舰队在没有人的情况下继续推进（窗口测量）

两次 census 快照之间，`census_delta.py` 给出：

```
census delta  2026-07-28T21:09:10Z -> 2026-07-28T23:41:47Z  (2.54h)
              29f41ea4 -> c3439767

  commits authored (any ref)              517 -> 552    +35   13.76/h
  commits landed on the mainline          397 -> 490    +93   36.56/h
  agent branches                           89 ->  91     +2
  PARTNER_SYNC paragraphs                 123 -> 136    +13    5.11/h
  agent->monitor inbox reports (ever)     103 -> 110     +7
```

两个提交数**不是一回事**，脚本拒绝把它们合并：`authored` 是新写出来的工作，
`landed` 跳得更快是因为一次合并会把早先写好的整条分支拉进来。把 `landed`
当产能会高估这个窗口，把 `authored` 当进度会低估真正落地的东西。

这个窗口的起止都钉在提交上，可以重算。**它能支撑什么、不能支撑什么**：
它测的是吞吐，不是「无人值守」——这个脚本看不见人的动作，
所以窗口内是否有人出手要去 `human_actions.jsonl` 查，而不是从这里推断。
另外，采集者（W-1641）自己就是窗口内的工人之一，是被测对象的一部分。

## 4. 组装本身

`assembly.jsonl` 19 行。**行为一律读机器写下的痕迹**（`board.log`、
`bus/*/{in,out}.jsonl`、`ops-status/*.json`），从不读契约对自己的描述——
这条纪律是 §0 第 3 条的执行形式。46 处引用逐条解析过。

### 4.1 契约即零件，克隆即继承

* **37 个 agent 实例出自 3 个契约家族，全部是克隆。** 逐字节相似度：
  运维类 68–70%，RES-1/2 之间 69%，RES-3/4 相对 RES-1 78%；
  25 个 W-* 工人全部从同一个模板起（`_runner.py:43`）。
* **一条子句，七个角色，一次提交。** `fb813ce` 加的「扇出纪律」整块在
  RES-1/2、OPS-A/B/M/R 与 `prompts/W-worker.md` 里 sha256 相同。
* **从「需要一个新角色」到「它在干活」：71 秒。** `6f6b87a` 在 15:06:39Z
  同时造出 RES-3 与 RES-4；RES-4 的第一条总线消息 15:07:50Z（+71s）、
  第一次板上领取 15:07:58Z（+79s）、第一件交付 16:05:16Z（+58m37s）。

**它没有证明什么**：78% 相同只说明克隆发生了，不说明被继承的四条纪律
（总线先行 / 手持 2–3 件 / 扇出硬要求 / 绝不停下）真的被遵守。那是另一次
测量，本次只在 A-09/A-11 拿到两份自述，未做核实。

### 4.2 热重调——测出来了，而契约的说法比测出来的强

四次真实重调，从改文件到**另一个已在运行的 agent** 行为改变：
**4分56秒 / 7分31秒 / 5分10秒 / 42分13秒**。最硬的一例：常驻研究员在
4小时16分里、跨 6 件条目始终只持 1 件，`fb813ce` 之后 7分31秒，RES-2
在同一秒里领了两件。

**但四次全部伴随一条总线或邮箱推送，零个「只改文件、不通知」的样本。**
所以被证明的机制是**「改文件 + 一行通知」**，不是「改文件」。契约自己的说法——
*改一个文件全队下一轮生效，不需要重贴启动词*——**仍然没有被证明**，
差的正是那条通知。

还测到一个天花板：OPS-A 在 15:03:32Z 报告**它的 harness 压过磁盘上的契约**，
使该子句对它不可执行——所以这条子句的最好成绩是 7 个角色里 6 个。

### 4.3 三个标准接口，各自的逼出事故

| 接口 | 引入提交 | UTC |
|---|---|---|
| 总线（in/out/cursor 三文件） | `15ecf80` | 14:20:18Z |
| 工作板（原子领取 + 领地互斥） | `32059928` | 06:00:40Z |
| 心跳（`ops-status/<ID>.json`） | `b23c110a` | 06:12:31Z |

三条因果链**都在引入它的那次提交自己的正文或 docstring 里写着**，不是事后追认。
但围绕它们流传的口号是民间说法，两处必须更正：

* **「邮箱延迟十二小时」不是测量**，那是 OPS-R 契约里的 720 分钟休眠值；
  邮箱总共只活了约 8 小时 19 分，**实测最长静默 8 小时 12 分 59 秒**（且从未被回执）。
* **心跳的提交说的是「闲着 vs 从未启动」**，不是「闲着 vs 掉线」。

而且 S17 工单里那两句口号（`逐件派单不可扩展`、`分不清闲着与掉线`）
**只出现在工单和 IDEA.md 里，两者都在本研究下游**——引用它们是循环，
所以数据集改引introducing commit 的原文。

三类失败在接口装好之后**都还复发过**：总线两次（含 RES-4 的队列死了 5 小时 05 分
无人取）；板 ≥5 次；心跳的时钟由 agent 自己手打且在漂移，
而 `needs_human` 阈值（900 分钟）比周期（720 分钟）还长，所以它几乎不可能触发。

### 4.4 自动供货：在有日志的窗口里是零

`monitor/reflex.log`（2026-07-28T03:16:26Z–23:56:18Z，读于 23:58Z）：
**`worker-spawn` 出现 0 次**，`worker-fail` 出现 124 次（分布在 28 行上）。
真正干活的 25 个 W-* 全都带手写风格的短 id（W-130、W-1630），
不是反射层生成的 5 位时间 id。板自己的引入提交写着：额外算力
「由用户打开 `monitor/worker.cmd` 窗口提供」。

W-1622 后来查出循环为什么完全死掉：`reflex.py` 用
`avail = len(board.candidates())` 且不带 lane，正是那个把带 lane 的条目
对普通工人藏起来的过滤器，于是 `avail == 0`，spawn 分支永远进不去。
（这与用户记忆里那条「BOARD-EMPTY 是假的」是同一个 bug 的两个受害者。）

**这一条直接顶着本研究的论点。** 组装权确实下放了，但**供货权没有**：
在这个窗口里，舰队的算力是人手动开窗口给的，不是它自己长出来的。
