## 0. 怎么读这份记录

四条纪律，写在最前面，因为它们决定了哪些数字可以信：

1. **每一行都能被打开。** `data/*.jsonl` 的每一行都带 `evidence`，形如
   `git:<sha>` 或 `file:<path>`；`verify.py` 会逐条解析——sha 必须
   `git cat-file -t` 得到 commit，路径必须存在于工作树或 git 历史。
   引用一个从未存在过的东西，本身就是本记录里的一个失败类
   （`requirement_cites_nonexistent`，5 例）。
2. **校验器必须能变红。** `verify.py --selftest` 注入 11 个人造缺陷，
   断言它逐个拒绝。理由写在脚本开头：本数据集里有一类叫
   `check_with_no_failing_path`（检查没有失败路径，3 例）——
   一个不会变红的校验器就是同一个缺陷，只是高了一层。
3. **系统的自我描述不是测量。** 契约声称「改一个文件全队下轮生效」是**主张**；
   证据是日志里另一个已在运行的 agent 的行为真的变了。二者不可互换，
   本记录中凡是只有前者的，一律标 `confidence: low` 并写明它不能证明什么。
4. **没发生的事同样是证据。** `counterevidence.jsonl` 与失败清单同等重要：
   装了没用上的机制、担心过却从未发生的失败、以及**被抓住的过度声称**。
   没有这一栏，任何系统记录都会滑向事后合理化。

## 2. 架构不是设计出来的，是被事故挤出来的

`timeline.jsonl` 记 45 次架构变更，从 `2026-07-27T18:13Z`（监控层诞生，
一个只读看板）到 `2026-07-28T15:06Z`（舰队补满 12 席）——**约 21 小时**。

按触发原因分：`friction` 22、`incident` 15、`design` 5、`user_request` 3。

**「45 次里只有 5 次是设计出来的」这个读数不成立，已被对抗性复核推翻**
（C-46，详见 §6）。原因是 `friction` 是个残差桶：T-02 自己写着「提交信息未点名
具体事故，**因此归为 friction**」——没有点名事故就是归入 friction 的规则。
机器可查的后果是 **22 行 friction 里，0 行在 `evidence` 中引用任何 `F-nn` 或
`INC-` 事故**（整个 45 行表都是 0）；它们引用的全是**被造出来的那个产物**，
证的是结果，从不证原因。而且结论早于数据：IDEA.md 在采集之前就写好了
「不是设计出来的，是被一次次事故逼出来的」和一张七条的清单。

**没有被推翻的是下面这张表。** 逐条读 timeline，多数行的事故叙事确有具体痕迹
支撑；塌掉的是那个 5:37 的**比例**，不是「架构由事故塑形」这件事本身。

被逼出来的链条，每一环都能在 `timeline.jsonl` 里查到触发它的那次事故：

| 事故 | 逼出的机制 | 时刻 |

| 从监控自己的 shell spawn 出来的东西活不下来 | 每 agent 一个一次性计划任务，提示词走 stdin | T-19, 03:49Z |

## 3. 舰队在没有人的情况下继续推进（窗口测量）

两次 census 快照之间，`census_delta.py` 给出：

```
census delta  2026-07-28T21:09:10Z -> 2026-07-28T23:41:47Z  (2.54h)
              29f41ea4 -> c3439767

  commits authored (any ref)              517 -> 552    +35   13.76/h
  commits landed on the mainline          397 -> 490    +93   36.56/h
  agent branches                           89 ->  91     +2
  PARTNER_SYNC paragraphs                 123 -> 136    +13    5.11/h
  agent->monitor inbox reports (ever)     103 -> 110     +7
```

两个提交数**不是一回事**，脚本拒绝把它们合并：`authored` 是新写出来的工作，
`landed` 跳得更快是因为一次合并会把早先写好的整条分支拉进来。把 `landed`
当产能会高估这个窗口，把 `authored` 当进度会低估真正落地的东西。

这个窗口的起止都钉在提交上，可以重算。**它能支撑什么、不能支撑什么**：
它测的是吞吐，不是「无人值守」——这个脚本看不见人的动作，
所以窗口内是否有人出手要去 `human_actions.jsonl` 查，而不是从这里推断。
另外，采集者（W-1641）自己就是窗口内的工人之一，是被测对象的一部分。
