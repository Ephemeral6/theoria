## 0. 怎么读这份记录

四条纪律，写在最前面，因为它们决定了哪些数字可以信：

1. **每一行都能被打开。** `data/*.jsonl` 的每一行都带 `evidence`，形如
   `git:<sha>` 或 `file:<path>`；`verify.py` 会逐条解析——sha 必须
   `git cat-file -t` 得到 commit，路径必须存在于工作树或 git 历史。
   引用一个从未存在过的东西，本身就是本记录里的一个失败类
   （`requirement_cites_nonexistent`，5 例）。
2. **校验器必须能变红。** `verify.py --selftest` 注入 11 个人造缺陷，
   断言它逐个拒绝。理由写在脚本开头：本数据集里有一类叫
   `check_with_no_failing_path`（检查没有失败路径，3 例）——
   一个不会变红的校验器就是同一个缺陷，只是高了一层。
3. **系统的自我描述不是测量。** 契约声称「改一个文件全队下轮生效」是**主张**；
   证据是日志里另一个已在运行的 agent 的行为真的变了。二者不可互换，
   本记录中凡是只有前者的，一律标 `confidence: low` 并写明它不能证明什么。
4. **没发生的事同样是证据。** `counterevidence.jsonl` 与失败清单同等重要：
   装了没用上的机制、担心过却从未发生的失败、以及**被抓住的过度声称**。
   没有这一栏，任何系统记录都会滑向事后合理化。

## 2. 架构不是设计出来的，是被事故挤出来的

`timeline.jsonl` 记 45 次架构变更，从 `2026-07-27T18:13Z`（监控层诞生，
一个只读看板）到 `2026-07-28T15:06Z`（舰队补满 12 席）——**约 21 小时**。

按触发原因分：`friction` 22、`incident` 15、`design` 5、`user_request` 3。

**「45 次里只有 5 次是设计出来的」这个读数不成立，已被对抗性复核推翻**
（C-46，详见 §6）。原因是 `friction` 是个残差桶：T-02 自己写着「提交信息未点名
具体事故，**因此归为 friction**」——没有点名事故就是归入 friction 的规则。
机器可查的后果是 **22 行 friction 里，0 行在 `evidence` 中引用任何 `F-nn` 或
`INC-` 事故**（整个 45 行表都是 0）；它们引用的全是**被造出来的那个产物**，
证的是结果，从不证原因。而且结论早于数据：IDEA.md 在采集之前就写好了
「不是设计出来的，是被一次次事故逼出来的」和一张七条的清单。

**没有被推翻的是下面这张表。** 逐条读 timeline，多数行的事故叙事确有具体痕迹
支撑；塌掉的是那个 5:37 的**比例**，不是「架构由事故塑形」这件事本身。

## 3. 舰队在没有人的情况下继续推进（窗口测量）

两次 census 快照之间，`census_delta.py` 给出：

```
census delta  2026-07-28T21:09:10Z -> 2026-07-28T23:41:47Z  (2.54h)
              29f41ea4 -> c3439767

  commits authored (any ref)              517 -> 552    +35   13.76/h
  commits landed on the mainline          397 -> 490    +93   36.56/h
  agent branches                           89 ->  91     +2
  PARTNER_SYNC paragraphs                 123 -> 136    +13    5.11/h
  agent->monitor inbox reports (ever)     103 -> 110     +7
```

两个提交数**不是一回事**，脚本拒绝把它们合并：`authored` 是新写出来的工作，
`landed` 跳得更快是因为一次合并会把早先写好的整条分支拉进来。把 `landed`
当产能会高估这个窗口，把 `authored` 当进度会低估真正落地的东西。

这个窗口的起止都钉在提交上，可以重算。**它能支撑什么、不能支撑什么**：
它测的是吞吐，不是「无人值守」——这个脚本看不见人的动作，
所以窗口内是否有人出手要去 `human_actions.jsonl` 查，而不是从这里推断。
另外，采集者（W-1641）自己就是窗口内的工人之一，是被测对象的一部分。

## 4. 组装本身

`assembly.jsonl` 19 行。**行为一律读机器写下的痕迹**（`board.log`、
`bus/*/{in,out}.jsonl`、`ops-status/*.json`），从不读契约对自己的描述——
这条纪律是 §0 第 3 条的执行形式。46 处引用逐条解析过。

### 4.1 契约即零件，克隆即继承

* **37 个 agent 实例出自 3 个契约家族，全部是克隆。** 逐字节相似度：
  运维类 68–70%，RES-1/2 之间 69%，RES-3/4 相对 RES-1 78%；
  25 个 W-* 工人全部从同一个模板起（`_runner.py:43`）。
* **一条子句，七个角色，一次提交。** `fb813ce` 加的「扇出纪律」整块在
  RES-1/2、OPS-A/B/M/R 与 `prompts/W-worker.md` 里 sha256 相同。
* **从「需要一个新角色」到「它在干活」：71 秒。** `6f6b87a` 在 15:06:39Z
  同时造出 RES-3 与 RES-4；RES-4 的第一条总线消息 15:07:50Z（+71s）、
  第一次板上领取 15:07:58Z（+79s）、第一件交付 16:05:16Z（+58m37s）。

**它没有证明什么**：78% 相同只说明克隆发生了，不说明被继承的四条纪律
（总线先行 / 手持 2–3 件 / 扇出硬要求 / 绝不停下）真的被遵守。那是另一次
测量，本次只在 A-09/A-11 拿到两份自述，未做核实。

### 4.2 热重调——测出来了，而契约的说法比测出来的强

四次真实重调，从改文件到**另一个已在运行的 agent** 行为改变：
**4分56秒 / 7分31秒 / 5分10秒 / 42分13秒**。最硬的一例：常驻研究员在
4小时16分里、跨 6 件条目始终只持 1 件，`fb813ce` 之后 7分31秒，RES-2
在同一秒里领了两件。

**但四次全部伴随一条总线或邮箱推送，零个「只改文件、不通知」的样本。**
所以被证明的机制是**「改文件 + 一行通知」**，不是「改文件」。契约自己的说法——
*改一个文件全队下一轮生效，不需要重贴启动词*——**仍然没有被证明**，
差的正是那条通知。

还测到一个天花板：OPS-A 在 15:03:32Z 报告**它的 harness 压过磁盘上的契约**，
使该子句对它不可执行——所以这条子句的最好成绩是 7 个角色里 6 个。

### 4.3 三个标准接口，各自的逼出事故

| 接口 | 引入提交 | UTC |
|---|---|---|
| 总线（in/out/cursor 三文件） | `15ecf80` | 14:20:18Z |
| 工作板（原子领取 + 领地互斥） | `32059928` | 06:00:40Z |
| 心跳（`ops-status/<ID>.json`） | `b23c110a` | 06:12:31Z |

三条因果链**都在引入它的那次提交自己的正文或 docstring 里写着**，不是事后追认。
但围绕它们流传的口号是民间说法，两处必须更正：

* **「邮箱延迟十二小时」不是测量**，那是 OPS-R 契约里的 720 分钟休眠值；
  邮箱总共只活了约 8 小时 19 分，**实测最长静默 8 小时 12 分 59 秒**（且从未被回执）。
* **心跳的提交说的是「闲着 vs 从未启动」**，不是「闲着 vs 掉线」。

而且 S17 工单里那两句口号（`逐件派单不可扩展`、`分不清闲着与掉线`）
**只出现在工单和 IDEA.md 里，两者都在本研究下游**——引用它们是循环，
所以数据集改引introducing commit 的原文。

三类失败在接口装好之后**都还复发过**：总线两次（含 RES-4 的队列死了 5 小时 05 分
无人取）；板 ≥5 次；心跳的时钟由 agent 自己手打且在漂移。

心跳还有一处调参使它几乎无法报警：`needs_human` 的阈值按角色设
（OPS-A 120 分钟、OPS-M 180、OPS-B 240、RES-1..4 各 90、**OPS-R 900**），
而 OPS-R 的周期本身是 720 分钟——**它的阈值比它的周期还长**，
所以对这个角色，「掉线」在正常运转下就够不着门槛。
实测：OPS-R 静默 538 分钟，无告警（C-09，其标题一句话说完——
「这个升级机制被调成了对最可能已经死掉的那个角色永远不会触发」）。

### 4.4 自动供货：在有日志的窗口里是零

`monitor/reflex.log`（2026-07-28T03:16:26Z–23:56:18Z，读于 23:58Z）：
**`worker-spawn` 出现 0 次**，`worker-fail` 出现 124 次（分布在 28 行上）。
真正干活的 25 个 W-* 全都带手写风格的短 id（W-130、W-1630），
不是反射层生成的 5 位时间 id。板自己的引入提交写着：额外算力
「由用户打开 `monitor/worker.cmd` 窗口提供」。

W-1622 后来查出循环为什么完全死掉：`reflex.py` 用
`avail = len(board.candidates())` 且不带 lane，正是那个把带 lane 的条目
对普通工人藏起来的过滤器，于是 `avail == 0`，spawn 分支永远进不去。
（这与用户记忆里那条「BOARD-EMPTY 是假的」是同一个 bug 的两个受害者。）

**这一条直接顶着本研究的论点。** 组装权确实下放了，但**供货权没有**：
在这个窗口里，舰队的算力是人手动开窗口给的，不是它自己长出来的。

## 5. 人类动作账

`human_actions.jsonl` **26 行**，`2026-07-27T10:50Z` → `2026-07-28T19:04Z`，
约 32 小时，期间舰队从 0 长到 12 席。

| 类别 | n | | 类别 | n |
|---|---:|---|---|---:|
| `paste_launch_prompt` | 9 | | `manual_trigger` | 2 |
| `adjudicate_direction` | 3 | | `oauth_or_credential` | 2 |
| `correct_the_agent` | 3 | | `grant_permission` | 1 |
| `delegate_authority` | 2 | | `supply_infrastructure` | 1 |
| `approve_budget` | 2 | | `request_feature` | 1 |

### 先说这张表为什么不能直接用来支持论点

**采集方法系统性地偏向「短」，而短正是论点想要的答案。** 三条，必须一起读：

1. **26 行里只有 1 行的时刻是 `exact`，其余 25 行是 `inferred`**——
   靠前后提交与日志夹逼出来的。
2. **凡是没有留下提交、文件或总线消息的人类发言，这张表看不见。**
   采集者明确把这一条列为「无法确定」。对话里的一句「不对，换个方向」
   如果没被 agent 写进任何文件，就不存在于这份记录。
3. **粘贴次数是下界。** 9 行 `paste_launch_prompt` 覆盖约 19 次粘贴，
   但监控自己有「转世纪律」——每约 3 小时重启一次以避开 5 小时配额窗口，
   这意味着还有一批「继续」类粘贴不留痕迹；提交不记录是哪个会话写的。

所以正确的读法是：**26 是人类动作的下界，不是总数。**
这张表能支持「人类动作很少」，不能支持「人类动作只有 26 次」。

### 表里真正硬的部分

**7/26 行自述「原则上可以自动化」**——采集者被要求，凡是本可以自动化的就照实说。
这是这张表里最诚实的一栏，也是对论点的反向证据：其中包括确认堆切分（H-04）、
批准装工具链（H-06）、粘一张监控自己刚写好的工单（H-09）、
废掉流水号（H-11）、要一个盘面视图（H-17）、手动戳两个停住的研究员（H-20）、
提出把舰队本身写成论文（H-23）。

**不可自动化的那 19 行，形状很清楚**：需要人的**身份**（两次 OAuth、
一次把 API 密钥放进 `.env`、一次装浏览器扩展）、需要人的**钱**
（两次预算批准）、需要人的**意图**（三次裁决方向、三次纠正 agent）。

**两次组装权下放本身**，是这张表里最关键的两行：

* **H-07（2026-07-27T18:13Z）** 造出「只监控、从不执行」这个角色。
  后面所有机制——工作板、总线、反射层、契约——都是它的后代。
* **H-19（2026-07-28T14:12Z）** 给出常设授权：启动、停止、扩缩、改派、派单
  都不必再问，只保留闸门之外的花钱与人类身份两项。此后人数变成
  `min(ceiling, 可领条目数)`，硬约束只剩物理的。

**H-21（15:07Z）是组装权买到了什么的最锐利一次测量**：两次粘贴立起 RES-3 与
RES-4，而它们的契约是监控在 **80 秒前**从 RES-1 克隆出来的（§4.1）。
角色的**设计**成本降到接近零，角色的**启动**成本仍是一次粘贴。

### 表没有在收敛

**最后一行不是粘启动词，是重启死掉的会话。** H-26（19:04Z）：四个常驻研究员
全部死亡后，人类重开 RES-3。H-20（14:50Z）是同一形状——手动戳两个停住的研究员。
再加上 §4.4 的实测（`worker-spawn` 为 0，算力靠人开 `worker.cmd` 窗口），
**人类在这 32 小时里的角色不是单调退化到「粘一行启动词」，
而是「粘一行启动词 + 把死掉的东西重新扶起来」**。
第二项没有随时间减少，它随舰队变大而变多。

## 6. 对抗性复核：四个头部数字，三个没站住

一个 subagent 被指派**去推翻而不是去确认**，默认立场是「这个数字支撑不了那个
结论」。它的每一条可机器判定的主张，本会话都独立复算过一遍才写进来。
结论落在 `counterevidence.jsonl` 的 C-44…C-49。

| 数字 | 裁决 |
|---|---|
| 96 起失败里 88 起往令人安心的方向失效（92%） | **推翻**（C-44）：抽样框的产出率，不是基础率 |
| 63/96 在修复后复发（66%） | **推翻**（C-45）：字段把四种事实合成一个布尔值 |
| 45 次架构变更只有 5 次是设计的 | **推翻**（C-46）：`friction` 是残差桶，结论早于数据 |
| 封存堆零接触，18,365 条请求体 | **成立，需改写**（C-47）：核心零值经独立复算与负控 |

**C-44** 采集 `failures.jsonl` 的 agent 是 RES-4，而 T-45 记着 RES-4 被造出来的
理由就是「四起无声失效且全部往令人安心的方向失败」，岗位职责写明「专盯静默失败」。
**结论是采集者的前提。** 另一个独立抽样框（340 个判断点普查）给出 48，即 14%。
`direction` 在整个仓库里没有定义，`neutral` 在 96 行中用了 **0** 次。

**C-45** `timeline.jsonl` 有 `recurred_after` **和** `recurrence_evidence` 两栏，
`failures.jsonl` 一栏都没有。4 行同时是 `fix: null` 与 `recurred: true`
（F-20/F-36/F-59/F-66），另 ≥8 行正文自述从未修好。F-66 甚至写着
「found before further spend, not after」——没有任何东西复发过。
**这条现在由机器抓：** `verify.py` 新增一条警告，正好命中那四行。

**C-46** 22 行 `friction` 中，`evidence` 引用任何事故 id 的有 **0** 行
（整张 45 行表都是 0）；它们引用的全是被造出来的那个产物，证结果不证原因。
而 IDEA.md 在采集之前就写好了答案和一张七条清单。

**C-47** 成立的部分很硬：18,365 精确复现，且**负控通过**——同一份代码同一个字段，
4 个开发堆 id 命中合计 17,857 次，证明这个搜索有失败路径。需改写的是三处：
「87 个文件」今天是 93 且不可能稳定（93 减去 6 个 pytest 残留正好 87）；
同句的「18,648 条 HTTP 记录」四种判据下都得 18,461；
**78% 的语料在未跟踪文件里**，干净克隆只能复算出 4,051 条。
准确说法是**零次请求指向封存局**，不是零次出现——21 个封存 id 都在
`GET /api/games` 的**响应**里出现过。

**C-48** 把 C-16 量化了：承诺这条纪律的出厂检查器 `contamination.py`
扫 **3 个**文件（实际 93 个）、**没有任何一处负控**、
且第 338 行的退出码只取决于一次 sha256 比对——**真出一次封存接触，它绿灯退出。**

**C-49** 签发本工单的那张工单，六个头部数字里五个无法裁决——不是因为错，
而是因为没有一个带口径或日期。唯一精确成立的那个（总线 28）在写下时是对的，
八小时后总线已是四倍，而它从未被标注日期，也从未被修订。

## 7. 缺口与不确定（诚实条款）

**这份记录里最该被怀疑的，是它自己。** §6 的六条全部指向本数据集，不是指向舰队。

### 已知缺口

1. **`direction` 与 `recurred` 两栏不可用**（C-44/C-45）。要修，需要
   `failures.jsonl` 补一个 `recurrence_evidence` 栏并逐行重裁——本次没做，
   因为改写第一手记录去迎合事后写的检查器，正是这份数据集自己在编目的那种倒推。
2. **`trigger_kind` 不可用作比例**（C-46）。要修，需要每行 `trigger` 带一个
   可解析的事故引用，当前 schema 不要求。
3. **克隆继承的是文本，不是纪律**（§4.1）。78% 的相似度不说明四条纪律被遵守。
4. **热重调只证明了「改文件 + 通知」**（§4.2），没有「只改文件」的样本。
5. **无法区分「舰队」与「监控」谁改了组装机器**：所有提交用同一个 git 身份，
   agent 归属只在提交信息与 `board.log` 里，不在作者字段（`census.json`
   的 `commits_by_author` 专门写了这条 caveat，免得有人拿它当舰队规模）。
6. **一个新角色要花几个人类动作，仍未确定**：仓库里不存在任何启动/粘贴日志
   （A-05，`confidence: low`）。

### n=1

一天、一台机器、一个人、无对照组。**照写，不解释、不辩护**——
IDEA.md 说存在性证明只需要一个，把它写成「局限性」反而是在暗示它本该有更多。
但要分清：`n=1` 是这个**舰队**的样本量；上面 §6 那些缺陷不是样本量问题，
是**测量问题**，不能拿 n=1 去解释掉。
