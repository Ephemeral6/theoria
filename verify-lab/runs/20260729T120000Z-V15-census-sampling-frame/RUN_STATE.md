1. **总体是 241 个单元**（把抽样框自己的三个工具也数进去后 243），
   V11 的 127 行覆盖 44.4%，negctl 的 141 条覆盖 58.1%。
   工单说的「74 个没判过」在新定义下是 **134 个**。
2. **补齐 126 行金标准**，全部盲于探针、全部 `读码`。
   「有负控 = 否」占 61%，V11 是 28% —— 便利样本系统性地偏向已被覆盖的一侧。
3. **矩阵：FP 3 / FN 20 → FP 6 / FN 41**（strict，同协议，分母从 95 涨到 219）。
   只看探针真正枚举的 145 个单元：**FP 1 / FN 36，FNR 从 39.6% 升到 50.7%**。
   新增的假阳一个都不在探针的总体里；变糟的是假阴。
   **V14 那句「不该进闸」被加强，其论据 4 的 FNR 数字要从 32% 改到约 51%。**

外加一条 V14 的空结果现在能说话了：`cold-start-a2/a2pipeline/engines.py`
盲判为「否」、判据为 `absent`、钉子为 `absent` —— 三者一致，是 TN。
**V14 的修是对的，只是当时的分母不允许矩阵这么说。**

## 对抗复核推翻/削弱了我什么 —— 逐条记账

对抗复核报告全文留在本目录 `ADVERSARIAL.md`。它的总判断是
**「加限定就够，不必重写」**，理由是它构造了 12 个替代总体定义（84 到 260 个单元），
**pinned 混淆矩阵在其中每一个下都逐格相同**（n 145，TP 35 / FN 36 / FP 1 / TN 73），
FNR 变化方向 12/12 一致 —— 一个怎么调都改不了自己答案的定义，不是为了让数字好看划的。
下面是它打动我的部分，以及我改了什么。**每一条都是原地记账，不是修完看不出错过。**

### 1. 盲判被破，而破它的是交付纪律本身

**指控成立。** `PARTNER_SYNC.md` 是 tracked、在仓库根、在九个判定员每一棵树里，
第 940 行载有 V11 的总计（`有负控「否」35`），第 958 行载有 V14 的 `FNR 32%`
**以及一条逐文件判定**：`worldgen/build.py` 被判 present —— 而那正是 pinned 矩阵里
唯一的那个假阳。

**这不是判定员偷看，是我设计的结构没挡住。** 我只想着删掉 `verify-lab/`，
没想到本仓库「每交付一件就往根目录一份 tracked 文件追加一段」的纪律，
会把答案复制到 `verify-lab/` 外面去。

我写了 `verify-lab/frame/leakage.py` 去量它，而不是嘴上说无害：
**126 条里 29 条（23%）**曝光；曝光组 present 率 **0.55**、未曝光组 **0.34**、
单侧二项 **p = 0.055**。对抗复核用略窄的词表得到 27 / 0.52 / 0.35 / p 0.121 ——
**我发布更狠的那一个**。方向对我们不利（曝光推向 present → 推高 FN → 正好抬高我的头条），
所以不许拿它当证据。**删掉全部 28 条可计分的曝光行重算：pinned FNR 0.507 → 0.484**，
仍远高于 V14 的 0.318，也高于只用 V11 金标准的 0.396 —— 泄漏解释不掉这个发现。
修法（下轮做，不是这轮）：判定员的树要 `git rm PARTNER_SYNC.md monitor/`，
或者从 orphan checkout 起；`leakage.py` 要在简报发出**之前**跑。

`BLINDING.md` 里那句「**no** counts, so it had no target to hit」**已撤回**，不是改写。

### 2. 「精确复现 V14」——撤回

**指控成立。** 四格里对上三格（TP 43 / FN 20 / FP 3），**分母差 2 行（95 vs 97）**，
因此 **TN 差 2（29 vs 31）、FPR 差 0.006（0.094 vs 0.088）**；harsh 侧同形
（TN 37 vs 39，FPR 0.245 vs 0.235）。我原来把差异归给「树的漂移」，**那是错的**：
差的是两行各指两个 `.py` 的普查行，`gold_v11` 要求正好一个所以丢了它们——
`theoria-arm/armtools/{salvage,timeline}.py`（gold 否、均判 absent，**正好是缺的 2 个 TN**）
与 `proxy/{canon,ledger}.py`（gold 是、均判 present）。

**最该记的一条**：`matrix.py` 的 docstring 原本给自己设的绊线
「落不到 FP 3 / FN 20 就说明协议有分歧」，**恰好只写在对得上的那两格上**。
写在结果吻合的那一半上的自检不是自检。现在 `--reproduction` 覆盖全部四格，
**且预期为不通过**。

顺带：那条「排除测试文件行」的规则被指控是事后凑的，**对抗复核自己去查了出处、
撤销了这条指控**（`CALIBRATION.md` 第 29 行在 V15 之前就写下了）。但我原来的注释
是用**结果**给它辩护的，那种写法读起来就是凑数，已改成用出处辩护。

### 3. 32% → 51% 的归因

**指控成立。** 我一次改了两件事（金标准 + 限制），却把全部涨幅记在补齐头上。拆开：
`0.317 →(只换限制) 0.396 →(126 条判定) 0.507`，**换限制占 42%**，harsh 侧占 56%。
换限制那一步 V14 当天就能自己算。**补齐值约 11pp，不是约 19pp。**

### 4. 58% 必须和 93–99% 并排登

**指控成立，而且这正是我在批评别人的那件事。** 58.1% 是拿探针去比一个
故意划得比它自己成员规则更宽的总体。按 V14 自己的规则（136 个单元）negctl 覆盖
**99.3%**；对抗复核略宽的读法（145 个单元）得 **93.1%**。两个数从此并排登。
立论不受影响：立论是「**V11 的金标准**只覆盖一半」，而 V11 在 V14 自己的规则下也只有 **50.7%**。

### 5. 两处事实错

* `BLINDING.md` §4 点名 `criterion.py` 为「无法盲判的第二个单元」——**它根本不是总体成员**
  （无 `__main__`、不抛仓库自定义异常，`frame.py --list` 里没有它）。真正被排除的是
  **`calibrate.py`**，`difference_set.txt` 第 122 行。**这个错的方向最坏**：
  `calibrate.py` 就是算出 V14 那份混淆矩阵的文件，是答案的可执行形式，
  也是最需要交代的那一处排除，而点错名恰好把它盖住了。已更正并补上理由。
* 同一个 run 目录里 frame 总数有 **241 / 243 / 244** 三个值，覆盖率 44.4% / 43.9%
  各出现过一次 —— 因为抽样框把自己的工具数进总体（这是对的），而**我每 commit 一次
  分母就变大、V11 覆盖率就被压低一点，方向恰好对我有利**。已加
  `BASELINE_REV = 3fa7170`（V11+V14 合并点，V15 尚未提交任何工具的那棵树），
  所有发布数字取在该修订；`--rev HEAD` 可看实时树。

### 6. `harsh` 下的反转，移到结论旁边

**不算指控，是它建议我别藏。** 在 `harsh` 折叠且**不加限制**时结论确实反转：
FNR 0.261 → 0.253（降），FP 12 → 17。pinned 限制下不反转（0.344 → 0.409，与 strict 同向），
而结论用的是 pinned，所以「不该进闸」站得住。**但这条脆弱性现在印在
`MATRIX_V15.md` §2 的结论旁与 `NEGATIVE_CONTROL.md` 的表下方，不在附录。**
相关：36 个 pinned FN 里 17 个来自 V15，其中 **10 个是 `部分`** ——
正是 `strict` 折叠算作「有负控」的那一档，也是九个判定员用得最不一致的一格。

### 它试了但没打动的（空结果也是结果）

* **造不出让 V11 覆盖率 >80% 的有原则总体。** 12 个变体，V11 覆盖率 41.9%–64.3%；
  上限是结构性的（127 行最多解析到 107 个文件级单元）。
* **分层 C 不是凑数**：拿掉它 V11 覆盖率**下降**（44.4→42.3%）、negctl 覆盖率上升，
  且它**从不进入混淆矩阵**（`gold_v15` 要求 `.py`）。指控撤销。
* **分层 B 是真旋钮（28–50）但动不了结论**：pinned 矩阵在所有改写下逐字节相同 ——
  探针枚举的每条路径都在分层 A 里。
* **「不要求能红」没有压低 FPR**：改回 V14 的规则后 FPR **下降**（0.056→0.049），
  因为被移除的多是 TN。指控撤销。
* **九个判定员之间无可测的判定员效应**：同名类零分歧；b3 的 present 率偏高
  （p 0.027，乘 9 批后 0.24）不显著。唯一真噪声通道是 `部分` 的用法差异，已记在上面第 6 条。
* **`读码`-only 的偏向是压低 FN 而不是抬高**，所以 **0.507 应读作下界**。
