## 一、缺陷复验成立

往 `runs/20260729T004020Z-leg01/` 扔一个 `scratch_notes.txt`（未跟踪、
且没有任何 `.gitignore` 规则匹配它）：

```
files[] 14 条 → 15 条，stray 进入了 files[]
```

`_files_the_clone_carries()` 只减掉「存在**且被忽略**」的文件，
从不问仓库「你到底装运什么」。check 8 重导并逐字节比对，
于是**同一个提交在持有那个 stray 的机器上绿、在克隆里红**——
正是 `46612a9c` / `6889b7e4` 声称已经终结的那件事。
仓库里没有任何被跟踪的 `.gitignore` 覆盖 `.DS_Store` / `Thumbs.db` /
`*.orig` / `*~` / `*.swp`，所以这不是假想的垃圾。

**所以 `backfill.py:1045` 与上一 leg RUN_STATE:103 的「答案不再取决于工作树」
确实写大了**，只关掉了「被忽略」那一类。这条订正成立。

## 二、推荐的修法（`git ls-files`）是错的，而且是量出来的

复核报告的原话是「The correct implementation is `git ls-files` (what the
repository ships), not `os.walk` minus `check-ignore`」。听起来对，
但 **`build()` 跑在这个 run 的产物被提交之前**。实测（全新 repo）：

| 状态 | `os.walk` 看到 | `git ls-files` 看到 |
|---|---|---|
| 产物在盘上、什么也没 stage | `certify.json` / `ledger.jsonl` / `turns.json` | **`[]`** |
| `git add -A` 之后 | 同上 | 三个都在 |

所以换成 `git ls-files`，**每一个新 run 的清单都会列零个文件**——
而 `verify.py` 的 `MIN_RUN_FILES` 下限是 8，manifest 当场不合格；
就算放过下限，产物一被提交，重导的答案就变了，check 8 立刻漂。

**这是本轮最该记住的一条**：一份对抗复核报告的**诊断**很强，
不代表它的**处方**被同样强度地检验过。诊断只需要找到一个反例，
处方要在所有调用点上成立。我这次没有直接照办，是因为上一世的教训
（一个恢复了字节稳定性的修法可以同时是错的）——**判断修法要看它把代价转移到哪里**。

## 三、缺陷的真实形状

**一个函数服务于产物生命周期里的两个时刻，而这两个时刻需要不同的答案。**

* `build()` 跑在**提交之前**：此时文件系统是**唯一**知道这些产物存在的来源；
* check 8 重导跑在**提交之后**：此时文件系统**同时**还持有别人扔在那儿的东西。

从文件系统上，「一件尚未 stage 的本 run 产物」和「某人的 `.DS_Store`」
**不可区分**。这才是缺陷所在，而不是「用错了 API」。

## 四、两个候选设计（都没实现，各自的代价照录）

### D1 —— check 8 不再重导 `files[]`，把它整个交给 check 10
比对时用 manifest 减去 `files[]` 的部分逐字节比，`files[]` 由 check 10 独占。
**收益**：check 8 的机器相关性被**移除**而不是搬家，且 `files[]` 的语义一个字不用改。
**代价**：check 8「byte for byte」的说法要加一条显式例外——
而这一带最不缺的就是说得比做得大的检查名，所以这条例外必须写进检查的名字里，
不能只写进注释。
**前置条件**：**必须先修 H3**。check 10 现在的判据是 `os.path.exists`，不是
「在克隆里」，把 `files[]` 路由给它等于把机器相关性搬过去而不是拿掉。

### D2 —— `files[]` 每条记录 build 时的 tracked-ness
让重导能分辨「未 stage 的产物」与「stray」。
**代价**：新字段，而且它是**从 build 抄来的**、不是重导出来的——
这正是 `_files_the_clone_carries` 的 docstring 自己用来拒绝「为被排除文件保留
sha256」的那条理由。用一条自己刚否掉的论证去支持一个新字段，需要先解释清楚为什么这次不同。

**推荐 D1，但 H3 先做。** 顺序反了就只是把缺陷挪个地方。
