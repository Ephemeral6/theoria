# monitor — 对着 Theoria.md 读工作树

一个只读的进度监视器。它把 `Theoria.md` 当作唯一基准，逐条对表工作树，
产出一页可刷新的 HTML。

```bash
python monitor/scan.py            # 重扫，重写 monitor/index.html
python monitor/scan.py --tests    # 顺带跑两条轨道的 pytest（慢）
```

然后用浏览器打开 `monitor/index.html`。

## 它为什么不属于任何一条轨道

`CLAUDE.md` 划的两条轨道是 `theory-compiler` 和 `engine-rig`，各自只碰自己的目录。
监视器是横切的：它必须读全仓，但**只写 `monitor/`**，不修改任何轨道的文件，
也不写 `PARTNER_SYNC.md`。所以它单独放在顶层，和 `arc-recon` 一样属于共同地面。

## 两类内容，页面上分得开

* **实况**（每次运行重新算）——文件是否落盘、候选流几条、封存堆有没有被碰、
  密钥有没有泄漏、pytest 什么结果。这些在 `scan.py` 的 `PROBES` 里，是代码。
* **判断**（人写的，带出处）——某条 Phase 1 验收项算不算达成、某条约束落实到什么程度。
  这些在 `spec.py` 里，每一行都注明它出自 `Theoria.md` 的哪一句。
  没有出处的行不该出现在那里。

页面上判断带 `clause` 标注，实况带「本次扫描」前缀。

## 每次运行都会重跑的两项硬纪律检查

1. **凭据卫生** —— 全仓扫描 `ARC_API_KEY` 的值，它必须只出现在 gitignore 掉的 `.env`。
2. **封存堆零接触** —— 把 `piles.json` 的封存 21 局与所有账本里出现过的
   请求体 `game_id` 求交集，必须为空。
   （目录列表里出现封存 ID 属于元数据，不算接触，检查器只看请求体。）

任一项变红都是 incident 级事件。

## 状态词表

| 词 | 意思 |
|---|---|
| 达成 | 该条满足，证据在磁盘上 |
| 部分 | 满足一半，note 里说清是哪一半没满足 |
| 有风险 | 有产物，但与基准文件矛盾 |
| 受阻 | 有工作，但要等别的东西先动 |
| 缺失 | 该条没有任何产物 |

## 局限

两条轨道并发工作，这份快照可能在写出的同时就过期了 —— 这不是缺陷，是重跑的理由。
`monitor/state.json` 是同一份数据的机器可读形态，可以拿去做时间序列。
