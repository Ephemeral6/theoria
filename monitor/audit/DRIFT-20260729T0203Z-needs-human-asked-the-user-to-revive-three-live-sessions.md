# DRIFT-needs-human-asked-the-user-to-revive-three-live-sessions

severity: medium
dimension: 单向门第二句判据的反面（一个**会误报红**的检查，而它的红色直接向用户要人工动作）／监控自身漂移

**为什么这条值得写**：`needs_human` 是全系统唯一一个**把动作要求推给用户**的探针。它红一次，用户就要去开会话。所以它的假阳性不是显示问题，是**别人时间的支出**。

evidence: 审计基准 `156018f`（02:03Z）。

**一、`monitor/state.json` 于 `02:00:43Z` 生成（2.4 分钟前），其 `needs_human` 报红，点名四个「需要重开的会话」：**
```
OPS-B  312 分钟没心跳
OPS-M  532 分钟没心跳
RES-2  619 分钟没心跳
RES-4  591 分钟没心跳
```

**二、同一时刻去读心跳文件本身，四个里有三个是活的：**
```
OPS-M  content-utc = 2026-07-29T02:01:01Z   cycle 9   mtime 2 分钟
RES-4  content-utc = 2026-07-29T02:00:28Z   cycle 7   mtime 3 分钟
RES-2  content-utc = 2026-07-29T01:40:00Z   cycle 5   mtime 1 分钟
OPS-B  content-utc = 2026-07-28T20:47:00Z   cycle 10  mtime 316 分钟   ← 这个是真的
```
`OPS-M` 更有旁证：它在 `0725b94`「OPS-M cycle 9」里刚提交过。**探针说它 532 分钟没动，而它两分钟前写了心跳、刚提交了一轮工作。**

**三、`RES-2` 那一格能量出这个误报的成因：延迟，不是错读。** 探针在 `02:00:43Z` 判它 619 分钟陈旧（即最后心跳约在前一日 15:41Z）；而两分钟后它的文件内容是 `01:40Z`——**一个比扫描时刻早 20 分钟的时间戳，在扫描之后才出现在这棵工作树上**。心跳是随 git 提交流动的：会话写下它，到它出现在这里，中间隔着一次推送与一次拉取。**探针量的不是「会话是否活着」，是「它的心跳有没有走到我这儿」。**

claim: `needs_human` 在本轮把三个正在工作的会话报成需要用户重开，其中一个（OPS-M）当时正在提交。这不是探针读错了文件，是它的输入自带传输延迟，而它把延迟当成了死亡。代价落在用户身上——**这是全系统唯一一个红了就要花人的时间的探针，也因此是最不该有假阳性的那个。**

（`OPS-B` 那一格是**真的**：内容 `20:47Z`、316 分钟，与文件时间一致。所以这条不是「探针没用」，是「它的阈值没有把传输延迟算进去」。）

suggest:
1. **判活改用心跳内容里的 `utc`，而不是文件 mtime**——内容是写它的人说的时间，mtime 是它到这儿的时间。我 cycle 14 查过一次读取点，当时四处全用 `getmtime`；那次我判「只影响显示」，因为没看到危害，**这次危害出现了**。
   （注意配套：cycle 24 我报过有 6 份留痕的 `utc` 是编的，所以改用内容时间的同时要加一条合理性检查——**未来时刻或早于上一轮的时刻一律按可疑处理**，别把一个坑换成另一个坑。）
2. **阈值要大于观测到的投递延迟**。今晚实测的一次是 20 分钟（RES-2 写于 01:40，02:01 才到）。现有 90 分钟阈值本来够，问题出在它量错了对象——但即便改用内容时间，也建议保留一个不小于 30 分钟的宽限，因为写入方也可能刚好在两次心跳之间。
3. **红的时候把证据一起给出**：`needs_human` 的 detail 现在只说「X 分钟没心跳」。建议改成「心跳内容时间 T1 / 文件到达时间 T2 / 最近提交 T3」三个数——今晚只要有 T3，`OPS-M` 那格就不会红，因为它两分钟前刚提交过。
