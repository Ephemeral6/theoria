## 附：本轮实测到一个更好的 append_only 判据（第 1 条的落地口径）

本轮红线扫描在区间内扫出 PARTNER_SYNC.md 的**第二笔删除**，查完判定**不是违规**，但它正好说明现判据错在哪：

- `6dec6f7`（14:57:33）就地改写了 `35d3a2c`（14:34:49）发布的段落的「下一步：」一行（X-3/X-4 那条表达力反馈引错了账目，改成了实测结论）。相隔 23 分钟。
- 但两笔**都在 `agent/c2-semantics-migrate` 分支上**，一起随 `84e9a26`（15:55）进的 master。**master 从未见过被改之前的那一版**，对方轨道在共享板上根本读不到错的版本。这在实质上就是「同窗口自我订正」，且比 `63ef0bf` 那次更干净。
- 现判据（全历史 `git log --numstat`）**会把它算成违规**，因为它数的是每一个分支提交，而不是共享板上真正发生过的事。

实测对照（可复核）：

```
git log --numstat -- PARTNER_SYNC.md                 → 2 笔删除提交
git log --first-parent --numstat -- PARTNER_SYNC.md  → 累计删除 1 行（只剩 63ef0bf）
```

**建议把第 1 条的修法定成 `--first-parent` 而不是豁免表**：append-only 纪律管的是「已发布给别人看的东西不能被悄悄改掉」，那么该被审的就是**主线一等父历史**——分支上自己改自己、合并前修干净，本来就该允许，不必逐条豁免。这样 `63ef0bf` 仍会被抓到（它是直接落在主线上的），而每一次合并前的自我订正自动不计。豁免表仍需要一条，但只需要 `63ef0bf` 那一条，且从此不会再增长。
