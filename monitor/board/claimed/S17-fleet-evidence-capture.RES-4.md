## 论点（本轮由用户点明，它决定了该收集什么）

这份记录的论点**不是**「我们搭了一支 agent 舰队」——那个已经有人做。论点是：

> **一个 agent 被交付组装权，用标准化封装的 agent 作为零件把舰队装起来并持续
> 改装，人类的动作退化为粘一行启动词。**

所以证据的重心是**组装本身**，不只是舰队的产出。必须钉住的四类：

1. **契约即零件、克隆即继承**——RES-3 与 RES-4 是拿 RES-1 的现行契约克隆、
   替换身份与方向两段造出来的，因此自动继承了当天积累的全部纪律（总线先行、
   同时持有 2–3 件、扇出硬要求、绝不停下来等人）。记下：从「需要一个新角色」
   到「它在干活」花了多久、人类做了几个动作。
2. **热重调**——契约每周期重读，改一个文件全队下一轮生效，无需重贴启动词。
   记下实际发生过的重调次数与生效延迟。
3. **标准接口**——总线（回执 + 打断）、工作板（原子领取 + 领地互斥）、心跳。
   记下每个接口是被哪次事故逼出来的（邮箱延迟 12 小时 → 总线；逐件派单不可扩展
   → 工作板；分不清「闲着」与「掉线」→ 心跳）。
4. **人类动作账**——**这是最硬的一条量化**：整段时间里人类实际做了哪些不可
   自动化的动作（粘启动词 N 次、完成一次 OAuth、批准一次预算……），逐条列出。
   组装权下放的价值就等于这张表有多短。

**诚实条款**（必须写进去）：不声称「世界第一」——无法核实。写成描述性的：
精确定义这个模式，说明它与已有工作的差别（claude-fleet 是人写框架、agent 当
工人；官方 agent teams 是队长委派、角色不由 agent 写成磁盘契约），把证据摆出来
让读者判断。报机制与代价，不报优先权。n=1、一天、无对照组，照写。

**这件最急，因为证据会腐烂**。今天一天这套舰队产生了一份关于「多 agent 协作如何真实失败」的一手记录：325 个提交、32 件板上交付、25 条事故、17 份 agent 上报、114 段同步板、28 条总线消息。但日志会滚动、决策的「当时为什么这么判」会随上下文蒸发——**再过两天就只剩结论、没有过程**。

做一件事：把它固化成 `fleet-study/EVIDENCE.md` + 结构化数据。要点：
(1) **失败分类学**，每条带 git 提交号与原始报告路径。已知四类，请从痕迹里补全并找反例：**悄悄失败**（判断在编码/并发/缺省上无声失效，且全部往令人安心的方向失败——今天四起：UTF-8 匹配 GBK 把八个活工人报成死、死工人认领永不释放让板替死人占领地、总线状态误报已回执其实一个没读、闸门缺失但盘面全绿）；**宣告与事实脱节**（编排者自称已修的三次：没改／改了一半／改了没跑，全部由审计员抓出）；**共享资源无串行化**（两会话各算各的账污染了一份花过钱的测量）；**要求引用了不存在的东西**（工单点名 verify.sh 而它从未被造出）。
(2) **时间线**：从「监控只读扫描」到「12 agent 自助舰队」的每一次架构变更、触发它的具体事故、以及变更后是否复发。
(3) **反例同等重要**：哪些机制装了但从没派上用场、哪些担心过的失败从未发生（例如封存堆 3184 条请求体零接触、密钥零泄漏）。没发生的事同样是证据。
(4) 数据落 `fleet-study/data/*.jsonl`（事件、事故、交付、总线往来），供后续统计；
正文只引用，不重抄数字。

**只做记录与整理，不写论文正文**（那是后续工单）。
