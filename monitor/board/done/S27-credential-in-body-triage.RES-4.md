# S27-credential-in-body-triage · 八百零七条「请求体里有凭据」，没人知道是真是假

审计把这条列进「还不能证实」，理由很正当：`proxy/redact.py:271` **自称是启发式**，
而要判断那 807 条是不是真阳性，就得去读请求体——**读请求体本身有读到凭据的风险**，
所以审计员没读，这个判断是对的。

但它不能一直挂着：**807 次误报会让人把这条告警关掉，而那正是真泄漏溜过去的方式。**

做四件，全程不打印任何疑似凭据的**值**：

1. **只按形状分类，不看内容**：对每条记录算出「命中了哪条启发式、命中片段的长度、
   字符类别分布、是否出现在已知的字段名下（如 `authorization` / `api_key`）」，
   **落盘的只有这些元信息与 sha256**，绝不落原文。
2. **拿已知真值对一次**：`.env` 里那把钥匙的 sha256 是可算的（`client.py` 的
   `load_api_key` + `mask` 就是为此存在的）。**逐条比 sha256**——
   命中就是真泄漏且必须当作事故处理；一条都不命中，就是启发式在报噪声。
3. **按结论改判据**：真泄漏为零则收紧启发式并把误报率写进 `proxy/STATUS.md`；
   非零则**立刻按事故流程走**（这条比修启发式重要得多，不要顺序搞反）。
4. **负样本**：构造一个**假的**、形状像密钥但不是密钥的字符串走一次请求，
   断言它必须被拦下并记录——用假的，不要用真钥匙做测试。

**硬红线**：真钥匙的值不得写入任何被跟踪文件、任何日志、任何报告，
连一次都不行（CLAUDE.md 的密封纪律，逐字）。
