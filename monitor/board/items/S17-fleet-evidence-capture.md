# S17-fleet-evidence-capture · 抢救性证据固化：舰队自身的实验记录

**这件最急，因为证据会腐烂**。今天一天这套舰队产生了一份关于「多 agent 协作如何真实失败」的一手记录：325 个提交、32 件板上交付、25 条事故、17 份 agent 上报、114 段同步板、28 条总线消息。但日志会滚动、决策的「当时为什么这么判」会随上下文蒸发——**再过两天就只剩结论、没有过程**。

做一件事：把它固化成 `fleet-study/EVIDENCE.md` + 结构化数据。要点：
(1) **失败分类学**，每条带 git 提交号与原始报告路径。已知四类，请从痕迹里补全并找反例：**悄悄失败**（判断在编码/并发/缺省上无声失效，且全部往令人安心的方向失败——今天四起：UTF-8 匹配 GBK 把八个活工人报成死、死工人认领永不释放让板替死人占领地、总线状态误报已回执其实一个没读、闸门缺失但盘面全绿）；**宣告与事实脱节**（编排者自称已修的三次：没改／改了一半／改了没跑，全部由审计员抓出）；**共享资源无串行化**（两会话各算各的账污染了一份花过钱的测量）；**要求引用了不存在的东西**（工单点名 verify.sh 而它从未被造出）。
(2) **时间线**：从「监控只读扫描」到「12 agent 自助舰队」的每一次架构变更、触发它的具体事故、以及变更后是否复发。
(3) **反例同等重要**：哪些机制装了但从没派上用场、哪些担心过的失败从未发生（例如封存堆 3184 条请求体零接触、密钥零泄漏）。没发生的事同样是证据。
(4) 数据落 `fleet-study/data/*.jsonl`（事件、事故、交付、总线往来），供后续统计；
正文只引用，不重抄数字。

**只做记录与整理，不写论文正文**（那是后续工单）。
