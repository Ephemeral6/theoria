# E17-held-out-validation · 整个 rig 没有留出验证，所以「已测」很多时候是「在拟合它的数据上自洽」

`grep -ril "held_out\|held-out" engine-rig/engines engine-rig/tools` → **零命中**。
而 `zero_space.verify` 是**在拟合它的同一条轨迹上**复验的——按 GF(2) 的构造，
那近乎恒真，那句 `AssertionError` 几乎不可能触发。

**三条独立发现指向同一件事**（这是它排 p1 的理由）：
DECISIONS 的 D-003 明写 `zero_space` 只承诺**在观测证据上**守恒（那是边界，不是缺陷）；
E9 把 `g50t` 放在 `zero_space` 边界的**已测**一侧，而那一侧从来没有东西检查过正确性；
本轮发现整个 rig 没有留出验证。**它直接影响论文里每一处「已验证」的措辞。**

做三件，按代价排序，**做不完就按顺序停，把停在哪写清楚**：

1. **先把事实写进 `ENGINE_TABLE.md` 的边界列**——那张表的规矩是边界列不许空，
   而这一格现在是空的。这一件最便宜且不可省：**在有留出验证之前，
   论文不得把这些格子写成「已验证」，只能写「在观测证据上自洽」。**
2. **给 `zero_space` 与 `lp_potential` 各补一次真的留出验证**：
   拟合用一部分轨迹，复验用**没参与拟合**的那部分，报告命中率与失败例。
   数字是多少都要如实写——**这一件的价值全在那个数字，不在它好不好看**。
3. 若还有余力，把留出集的划分写成 rig 的一条常规（fixtures 生成时就切好），
   让后续引擎默认带留出验证，而不是靠记得。

**别把这件并进 E16。** E16 的验收线是两处判据接线，这件的验收线是一个新数字；
并在一起没人复核得动（A9 与 V16 都是这么切开的，且切对了）。

服务论文 WP1 与 WP9。零 API、零封存堆接触。
