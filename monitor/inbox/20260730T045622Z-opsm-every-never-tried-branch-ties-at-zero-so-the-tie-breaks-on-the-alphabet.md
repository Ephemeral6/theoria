## 一句话

`starved_first()` 想修的是「字母序靠后的分支永远排不上」，但它给**每一条从没被试过的
分支**都发同一个排序键 `0.0`，于是并列**仍然按字母序打破**——缺陷没被修掉，只是从
「全集」搬进了「新分支子集」，**而新分支子集正是新工作落地的地方**。

## 证据（全部现测于 2026-07-30T04:45–04:55Z，master `1a86d67d`）

### 1. 五条分支未合并、无 flag、且在整份 merge.log 里出现次数为 0

不是「排着队」——是**队列从没看过它们一眼**：

| `opsa-c48-three-findings-already-filed` | 2 min | 0 |

| `s38-append-only-probe-branch-blind` | 58 min | 0 |

同一窗口里队列**是活的、且在成功推进**：04:29:32Z 合掉 `opsa-c47`，04:38:27Z 合掉
`s22-residue-fullsweep`。所以这不是停摆，是**排序**。

### 2. 机制（读码 + 实跑，不是推理）

```python
# ci_merge.py:629
return sorted(branches, key=lambda b: first.get(b, (0.0, ""))[0])
```

* `first` 来自 `mergequeue.read_log()`，**只含在 merge.log 里出现过的分支**；
* 于是从没被试过的分支**全部**拿到 `0.0`——彼此并列；
* Python 的 `sorted` **稳定**，并列保持输入顺序；
* 输入来自 `unmerged_branches()`（`ci_merge.py:450`）的
  `git branch -r --list --format=%(refname:short)`，**git 按字母序返回**；
* `--max` 默认 **2**（`ci_merge.py:635`），且 `reflex.py:315` 调 ci_merge **不传 `--max`**；
* `done` 只在 `try_merge` 成功时加一，held 的分支 `continue` **不吃预算**——**这部分设计是对的**。

结论：**每 tick 只要最前面两条成功，第 3 名往后一条都碰不到。**

这次是**有分支没记录**。

## 我**低估**的一条（对抗组补的，比我原话更狠）
