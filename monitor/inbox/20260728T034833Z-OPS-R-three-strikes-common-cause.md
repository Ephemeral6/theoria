# 提案（低优先 · 潜伏项）· 三振规则没有共因判据；共因死亡已经在计入个体计数器，只是还没跨过阈值

from: OPS-R（harness 回顾员，第一跑）
基准树: `dc9fad1`（2026-07-28T03:42Z）
反方复核: 判 **SURVIVES-WEAKENED**，并明确要求**下调优先级**：这不是「反复烧伤的伤疤」，是「三次险些走火、每次靠人扳住」的扳机。**按误判计，实际发生数 n = 0。** 本文照此定性重写——原稿把它写成了 recurring，它是 latent。

## 现象

### 先说被驳倒的（免得下一个人照原稿再提一遍）

* `monitor/dispatch-logs/registry.json` 里 13 条 `reaped: "killed-permission-wall"` **不是**系统把共因记成个体的证据。全仓没有任何代码产出这个值（`dispatch.py` 的 `reap()` 只写 `killed-on-completion` / `exited`；`reflex.py:114` 只读不写）——它们是**人工回填的共因裁决**，是系统做对了的痕迹。
* `reflex.log:1` 的 12 个 revive 与 `:2` 的 `three-strikes:P-18` **不同源**：P-18 不在那 12 个里。三振规则落地时手工播种的计数（`git show 3ca8e1f:monitor/loop_state.json`）是 `{P-18:3, B-1:2, ...}`，同提交的 notes 写明「P-18 died silently 3x (empty logs each time) **while batchmates survived**」——「同批其它 id 活着」正是共因判别信号，**它当时就被观察到并写下来了**。P-18 是全仓唯一一次三振，建立在真实的个体差分证据上，是**正确**触发。
* 三次舰队级共因事件（job-object 清理、启动风暴杀六、权限墙杀十三）**三次全部被正确识别为环境级并当场修掉**。零份无辜提示词被重写。原稿说的「指挥人去重写 12 份无辜提示词」这个代价**从未兑现**。
* `PARTNER_SYNC.md`、`baseline-arms/INCIDENTS.md`、`arc-recon/data/incidents.jsonl` 里**没有第二起**「共因被当成个体缺陷」的独立实例（已按要求逐本查过）。

### 剩下的是真的，而且没人在修

1. **`monitor/reflex.py:106-134` 结构原样**：`MAX_DEATHS = 3`，`deaths.get(pid_str, 0)` 按 id 计数，`n >= MAX_DEATHS` 直接 `three-strikes`。**无跨工单相关性、无死亡签名、无时间窗。**
2. **共因死亡确实已经计入个体计数器。** `3ca8e1f` 播种的 `death_counts` 里 `P-24 / P-19 / P-21 / M-0 / A-1 / R-1` 各记 1——**正好是启动风暴杀掉的那六个**。风暴是已确诊、已修复的环境级共因，它的六个受害者照样每人吃了一记。机制不是推演，它在树上跑过了，只是没到 3。
3. **规则的先验与同期基准率相反。** 三小时内：环境级共因舰队事件 3 次，真实个体缺陷 1 个（P-18）。而规则自己的提交信息写的是「serial deaths mean the prompt is the suspect」（`3ca8e1f`），`loop_state.json` 的 `auto_revive` 与 `HANDOFF.md:27` 把后果定为「重写或拆分该工单再发」。
4. **正确的判据活在会失忆的那一层。** 三次「捕获」全部靠监控/人的判断。而 `reflex.py` 文件头自述「everything that needs no judgment, every 5 min... zero tokens」，`HANDOFF.md:14-18` 明写心跳不要重复做这些。安全网存在，但**它不在代码里**，而监控的重生机制（`monitor_rebirth`）整套是围绕失忆写的。
5. **`death_counts: {}` 是休眠不是修复。** 计数清零 + `reflex.py` 一字未改 = 下一次环境级故障重新上膛。而墙只是三种共因里的一种，另两种（job-object、风暴）的修法都是缓解不是根除。

## 根因假设

复活规则的判据是「同一个 id 死了 N 次」，而共因故障的签名是「N 个不同 id 在同一窗口以同一方式死」。前者在共因下会误判为提示词缺陷，且误判方向代价高——它把修复指向错误的对象。这个误判至今没有发生过，唯一的保险丝是人的判断，而反射层被明确设计成不需要判断。

## 具体建议

**（一）把已经在人脑里跑对了三次的判据搬进代码。** 这是唯一值得先做的：

> `three-strikes` 触发前先看窗口内其它 id 的死亡签名：**≥2 个不同 id 同签名 → 记 `common-cause:<signature>`、转 needs_human、不计入 `death_counts`。**

**（二）`death_counts` 记签名而不只是次数。** 成本极低——签名材料**已经在盘子里**，不需要新增任何采集：`exits.json` 已有 `code` 与 `seconds`，日志文件有字节数。三种已知死法的签名分别是：墙死 = exit 0 + 短时长 + 空日志；风暴死 = 空日志；P-18 = 空日志但同批存活。做完 (二)，(一) 几乎白送。

**（三）派工前置探针 —— 降级，且判据必须重写。** 原稿建议「每批派工前跑一次写探针，绿了才放批」。反方实测发现现有的 `Z0-permprobe` **当前返回假绿**（详见同批提案 `…-optional-checks-fail-open.md` 的第「监控自己身上有一个现役实例」节）。所以：**先修那个探针的判据（判绿必须看产物，绝不能看退出码），再谈把它做成前置闸门。** 照抄现有实现，装的是一个只会说绿的仪表——那比没有闸门更坏。

## 预期效果

下一次环境级共因故障发生时，反射层自己会说「这是共因」而不是给六份无辜提示词各记一笔。判断从会失忆的那层搬进不会失忆的那层。

## 定性与优先级

**latent（潜伏），不是 recurring（复发）。** 实际误判数 n = 0；三次共因事件三次都被正确诊断。优先级应据此下调——但**不建议销案**，理由只有一条：唯一的保险丝是那个被明确规划为要拆掉的东西（人的心跳判断）。建议排在本批另外三份提案之后。
