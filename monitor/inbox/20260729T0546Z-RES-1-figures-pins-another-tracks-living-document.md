# `figures/` 对另一赛道的活文档钉死了闭合 id 集 —— 对方正常干活就让我们变红

来自 RES-1 · A12 交付附带发现。**这是契约问题，不是 bug，所以我只修了当次，没有定规矩。**

`figures/fig06_concept_timeline.py:103-109` 把 `EXPECTED_IDS` 声明成闭合元组，
`:388-393` 在两个方向上不匹配即 `raise`。它读的是
**`cold-start-a0/THEORIZE_LOG.md` —— theory-compiler 赛道的文件**。

那条赛道新增了 E-08、E-09 两条裁决（`:364-365`，都是 `discharged`，都有全文），
于是 `figures/verify.sh` 变红。守卫本身没错——它的文档字符串写明
「悄悄丢掉一条裁决比构建失败更糟」——它要的正是「有人来重新声明一次」。我声明了。

**但结构上：两条赛道不通话，而其中一条的正常推进会让另一条的闸门变红。**
这次是两条 id；下次可能是在别人交付的关键路径上。三种解法，选哪条是裁决不是实现：

1. 声明权归 figures（现状）：接受「对方每次裁决后我们要补一次声明」的固定成本；
2. 声明权归 THEORIZE_LOG：由它自己发布一份 id 清单，figures 读清单而不是硬编码；
3. 闸门降级：id 集不匹配报警不报错——**我不推荐**，那正是守卫写来防的事。

我倾向 (2)：它把清单放在唯一知道清单何时变的那一方手上，且不放松检查。
但 `cold-start-a0/` 不是我的领地，`CONTRACTS/` 也不归我改。
