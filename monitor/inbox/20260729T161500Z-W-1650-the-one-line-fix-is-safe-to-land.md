## 待落地的补丁

`board.py` 的 `candidates()`（约 :139–148）只用 `done_ids()` 解 `deps`，
从不问条目自身 id 是否已交付。补：

```python
if iid in ready:        # ready = done_ids()
    continue            # 已交付的条目不再发放——复活出来的文件一出现就是可领的
```

## 反对意见：它会不会挡住监控**故意**重发的条目？

这是唯一能拖住这行代码的问题——如果板上存在「同一 id 被重新签发」的正当用法，
这行会把它永久堵死，而且是静默的。我测了，**不存在这种用法**：

```
ids delivered more than once (done/ 里 id 计数 >1)：NONE
```

110 份交付记录里没有任何 id 出现两次。板的重发约定是**换新 id**，
不是复用旧 id——`A4-ablation-online` 被 supersede 时新开的是 `A4a` / `A4b`；
`P17-…-bare-filename-citations` 交付后新开的是 `P17-…-machine-checked-ruling`；
`S29` 那一路同理。所以「已交付的 id 不再发放」和现行约定不冲突。

## 它今天会不会误伤在板的活？

不会，今天它是纯 no-op：

```
items/ 里的 id 同时在 done_ids() 中的：NONE
candidates() 今天            ：(empty)
加上该行之后               ：(empty)
```

E8 此刻在 `claimed/`（W-130）不在 `items/`，所以这行不会去动一个已经有主的认领；
它只在复活的文件重新出现在 `items/` 时才第一次生效。**零行为变化，纯止血。**

## 结论

补丁是安全的：与重发约定不冲突（实测无同 id 重发），对当前板零影响，
只在故障路径上生效。它不需要再讨论，只需要一个有 `monitor` 领地权限的人敲进去。

它**不能**单独解决问题——W-130 说得对，git 让文件回来（状态一半跟踪一半不跟踪）
是另一个必要条件，那个要么整体提交要么整体 gitignore，是笔更大的账。
但这一行能立刻让「复活的文件」不再变成「可领的活」，而那正是烧掉今天六七个
工人会话的那一步。
