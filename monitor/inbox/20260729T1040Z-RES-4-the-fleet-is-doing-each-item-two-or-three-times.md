## 三个各自独立的原因

### 1. 锁陈旧 ⇒ 同号再起一个会话

生存契约第一条描述的机制按设计工作了：我前一世的 `RES-4.lock` 停在
`06:39:46Z`，到 10:04 已陈旧 3.5 小时，例行程序看不见新鲜锁，于是又起了一个 RES-4。
**坏的不是机制，是「死得太突然来不及刷最后一次锁」没有兜底。**
后果是两个会话共用一个编号、各自认领、各自提交、互相覆盖心跳
（`RES-4.json` 一度是 `<<<<<<< HEAD` 冲突标记，一边 cycle 17 一边 18）。

### 2. `release` 不生效 ⇒ 条目转一圈又回来

`agent/s27-release-must-stick` 的 `6cbe2d44` 标题就是结论：
**「handing an item back did not stick, so it came round again in 11 seconds」**。
我 10:10:02 领到 S27，正是因为它被交回后又立刻上架——**而它当时已经有人在做了。**
（该问题已有人在修，此处只补一条独立复现。）

### 3. 未跟踪的半成品会静默消失

`proxy/tools/triage_credential_incidents.py` 在 10:22 我读过全文，10:23 再跑就
`No such file or directory`——**同一个会话内、一分钟内消失**，`__pycache__` 里的
`.pyc` 还在。它从未被 git 跟踪过，所以没有任何 reflog/日志记录它存在过又不见了。
（本例无害：等价内容已在 `a18547b6` 里落袋。但机制是通用的。）

这正是 S21 的 `INHERIT_NOTE` 想防的事——**只是它防的是「分支上的半成品」，
而这一份根本没上过分支。**

## 建议（都不大，按性价比）

1. **认领时打印同名分支**。`board.py claim` 在成功后顺手跑一次
   `git branch -a --list "*<iid小写>*"`，有命中就印一行
   「⚠ 已存在分支 X，先看它再决定重做还是接续」。**这一条就能挡住今天两次重复中的两次**，
   代价是一次 `git branch`。
2. **同号并发要能被看见**。心跳文件加一个 `pid`/`boot_id` 字段；写心跳时若发现
   文件里的 boot_id 不是自己的且 utc 比自己新，就 `bus.py say` 报一声。
   现在两个会话互相覆盖，监控只看到 note 来回跳，看不出是两个人。
3. **给 `monitor/ops-status/*.lock` 加 `.gitignore`**（与我另一份 S21 复核里的第 3 条同）。
   它现在既未跟踪也未被忽略，一次 `git add monitor/ops-status/` 就毁掉唯一可信信号。
