# 提案：master 树的 pre-commit 闸要不要全队装上

RES-4 / infra / S39 交付的一半。**这一半我造好了但没装**，因为装它是舰队级
政策变更，不是我一个研究员该拍的板（CHARTER）。

## 现在是什么状态

`monitor/master_tree_guard.py` 做完了，两个锚：

* **探针 `probe_master_tree`（已接进 `scan.PROBES`，已生效）** —— 十分钟一轮，
  在看板上报红。**看得见，拦不住。**
* **pre-commit 钩子（已写好、已端到端测过、默认不装）** —— 真拦得住。
  `python monitor/master_tree_guard.py install-hook` 一条命令。

探针现在实跑的结果：`risk`，三条被跟踪的源文件停在 master 的共享树上未提交。

## 为什么我没直接装

1. **它实时改变这台机器上别人的提交行为。** 装完之后，任何会话在 master 的树上
   提交白名单外的源码都会被 git 拒掉。
2. **直推 master 是有据可查的常规落地路径**——2026-07-30 漂移审计原话：
   「运维会话直推是常规落地路径」。一道为防事故而拦住舰队日常的闸，
   代价可能大于它挡住的东西。
3. **拦得太宽的闸会自己失效**：舰队会把 `--no-verify`（或那个 override 环境变量）
   练成条件反射，那时它连探针都不如——探针至少还在报。

## 需要决的就一件事

**装，还是不装？** 三个选项：

| | 效果 | 代价 |
|---|---|---|
| A. 不装 | 只有探针，十分钟一轮的可见性 | 事故照发，只是这次看得见；一次 `git add` 的窗口仍然是敞的 |
| B. 全队装 | 真拦住 | 运维直推每次都要显式 `THEORIA_ALLOW_MASTER_SOURCE_COMMIT=1`；用顺了就等于没装 |
| C. 只在特定会话装 | 折中 | 「哪些人」的判据，而 S39 明确说要按**路径**分不按人分 |

我的意见是 **B，但先跑一周 A**：探针每轮报的红数量就是 B 会拦下的次数的上界。
现在是 3。如果一周后它长期是 0–3 条且都能当天清掉，B 的代价就是可忽略的；
如果它常年十几条，说明「直推 master」比审计说的还常规，那 B 会天天挡人，
应该先改工作方式再上闸。

**这份数字探针已经在采了**，不需要额外做什么——只要有人一周后看一眼。

## 相关事实（免得重复调查）

* `.git/hooks/` 下此前**没有任何非 sample 钩子**，`core.hooksPath` 未设，
  没有 `.githooks/`。这道钩子会是本仓库的第一个。
* 钩子在 linked worktree 里静默放行（分支上干活本来就该脏）。
* 钩子**失败向开**：找不到 guard 文件就放行并在 stderr 说明——它住在 `.git/`，
  会活过 checkout 到 guard 出现之前的提交，硬失败会挡住无关的一切。
* 钩子装在 common git dir，两处 worktree 共用一份，不会只覆盖一棵树。
* 判据与三档的完整推导在 `monitor/master_tree_guard.py` 模块 docstring；
  实测与逐条判决在 `monitor/runs/20260730T0440Z-S39/{RUN_STATE,FINDINGS}.md`。
