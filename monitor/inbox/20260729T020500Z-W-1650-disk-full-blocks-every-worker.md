# 磁盘 100% 满，会以「测试莫名失败」的样子打在每个工人身上

工人 W-1650，领 E16-verdict-must-gate 时撞到。**这不是 E16 的事，是全队的事。**

## 现象

建完 worktree 跑基线 `pytest` 时：

```
OSError: [Errno 28] No space left on device
```

`df` 当时：`C: 474G 474G 3.2M 100%`。**剩 3.2 MB。**

危险的地方在于它**不长得像磁盘满**。第一次跑 `pytest -q` 退出码 0、输出只有一串
点，因为汇总行写不出去；我以为绿了。是第二次跑才把 ENOSPC 抛到脸上。
**退出码 0 + 输出被截断 = 这一模式和已记录的「假健康」签名同形**：判健康要看产物，
不能看退出码。任何工人在这段时间报「测试通过」都应当被当作未验证。

## 我做了什么（只做了无风险的一档）

只删了 `.worktrees/` 下 **1475 个 `__pycache__` / `.pytest_cache`**（gitignore、
纯生成物、重跑即回），外加 `git worktree prune`（只清目录已不存在的登记）。
**没有动任何人的 worktree 源码**——那里可能有在飞的活，删了不可逆，不是我该单方面做的决定。

结果：`474G 466G 8.8G 99%`。够我干活，**不够全队干很久**。

## 需要监控裁决的（我不动）

1. **`.worktrees/` 有约 100 个目录、10G。** 里面大量分支看起来早已合并
   （`p4-figures`、`s3-spend-gate`、`e2-fd-ladder-bench` …），还有 `_c1w_salvage`
   / `_e1_salvage` 这种一次性目录。**清理条件应当是「分支已并入 master」而不是
   「看起来旧」**，且要有人确认没有会话正在用。这需要一次带清单的裁决，不是随手删。
2. **仓库只占 14G / 474G。** 剩下 452G 在仓库外，不在任何工人的领地里，也不该由
   工人去猜。谁能看主机谁去看。
3. **建议加一条开工前置检查**：worktree 建好后先 `df`，剩余低于某阈值就直接
   `release` 并写 inbox，而不是让每个人各自撞一次再各自查一遍。我这次花在诊断上的
   时间，后面每个工人都会再花一遍。

## 边界

零 API、零网络、封存堆零接触、$0.00。删除只发生在 `.worktrees/` 下的
`__pycache__` 与 `.pytest_cache`，无被跟踪文件受影响。
