## 1. 问题：账本自洽，但不可信

P-9 的红队交了 46 条攻击，29 条打穿，全部修完。**只有一条没有本地修法**，它是
RED-40：

> 没有任何东西认证一条记录。手写的账本、臂写的账本、任何有文件写权限的东西
> 写出来的账本，只要写得够仔细，就能对账通过——对账器检查的是文件与它自己。

P-9 把伪造的**代价**抬高了：`frame_hash` 必须真的哈希它自己的帧（写入方直接
拒收）、`seq` 必须稠密且不重复、一个 run 只能属于一个臂、卡的合计必须与它自己
的 environments 相符、打分器裁决前先跑一遍 canon 校验器。**但代价不是证明。**
上面每一条都是自洽性检查，而伪造者可以写出自洽的文件。

**为什么这件事重要，以及为什么它不紧急。** Phase 1 的「不可绕行」一直是针对
**臂**说的——臂没有凭据、没有写账本的路径——那一条仍然成立，本提案不改变
Phase 1 门禁的任何一项。真正吃亏的是 **Phase 4**：释出时外部读者拿到的是一堆
JSONL 和一句「这是我们跑出来的」，而我们手上没有任何东西能把「代理写的」与
「事后写的」分开。`Theoria.md` 的整个立论是「结论只允许从账里来」；如果账本
本身只能靠作者的信誉，那句话就只对我们自己成立。

**所以本提案的真实截止时间是 Phase 4 释出前，不是 Phase 1 门禁前。** 这是本
提案请求监控裁决的第一件事：优先级。

## 2. 方案：逐记录哈希链 + 链头发布在文件之外

### 2.1 链本身

信封增加一个字段：

```json
{"v":"1.0","event":"env_step","seq":42,"prev":"sha256:1f0c…", …}
```

* `prev` = **前一行（写入磁盘的那一行字节，含它自己的 `prev`）** 的 sha256。
* 文件第一行 `prev: null`。
* 校验方式极其简单：逐行读文件，哈希上一行，与本行的 `prev` 比对。**不需要
  重新规范化 JSON**，因此不依赖任何两个写入方对 canonical 拼写达成一致——这
  一点是刻意的，`canonical()` 只要有一天改了行为，重算式的校验就会全线变红，
  而按字节的校验不会。

改一行 ⇒ 其后每一行的 `prev` 全部对不上。删一行、插一行、调换两行，同理。

### 2.2 链头：唯一让它有意义的部分

**链本身不阻止任何人重写整个文件并重算全链。** 让它有意义的是链头发布在文件
之外，且发布得比伪造早。

提议：**链头进 `runs/<prompt>/MANIFEST.json`，随分支提交进 git，push 到远端。**

```json
"ledger_head": {"path":"proxy/var/ledger.jsonl","last_seq":1153,
                "sha256":"sha256:9a4e…","published_at":"2026-07-28T21:44:00Z"}
```

理由：git 的提交本身就是一条哈希链，而仓库会 push 到远端，于是见证在**另一台
机器上**。伪造一份账本就得同时重写 git 历史与远端——那是一个可检测得多、也贵
得多的动作。而且这条路子零新增基础设施：`runs/` 归档与 MANIFEST 是本仓库已经
在做的事（M-0 的「留痕门」）。

### 2.3 不升版本，因此不惊动任何人

**`prev` 是可选字段，`v` 保持 `1.0`。**

`LEDGER_FORMAT.md` §1 说字段只能追加；§8 说升 `v` 的条件是「字段含义改变」或
「新增必填字段」。可选的 `prev` 两者都不是，于是：

* battery 的适配器不必改一行，v1.0 读者照读；
* 三臂不必协调；
* 已有的 `proxy/var/ledger.jsonl` 与提升产物继续有效。

代价是显然的反问：**可选字段不是形同虚设吗？伪造者不写 `prev` 不就绕过了？**
不能，因为强制不来自格式，来自链头：

* `run_start` 声明 `chain: {"enabled": true, "from_seq": N}`；
* MANIFEST 的 `ledger_head` 声明这条链应该有多长、头是什么；
* 校验器在两者存在时**要求链完整**，缺 `prev` 即失败。

于是「不写 `prev`」和「写错 `prev`」一样是可检测的，而**不写链头**是一个必须
由人做出、并且在 git 里留痕的决定。这比把 `prev` 设成必填强，因为必填只会让
v1.0 读者集体报废。

> **一处对本轨道自己的订正**：`proxy/DECISIONS.md` D-024 写的是这件事「要改
> 信封、要升版本、要与三臂和电池协商」。把 `prev` 设为可选之后**这三样都不
> 需要**。D-024 的判断当时偏保守，本提案落地时会在 DECISIONS 里更正。

### 2.4 分片与合并

`baseline-arms` 按进程分片再合并（`merge_ledger.py`），链是**按文件**的，合并
会破链。处置：合并产物是一个**新文件、新链**，并在它的首条记录里记下每个源文
件的路径与链头。合并不是伪造，但它是一次改写；把它记成一次改写，而不是假装
链穿过去了。

### 2.5 提升（迁移）的流不上链

v0 存量账本没有链，而事后由同一方补一条链毫无证据价值——头是伪造者自己发布
的。处置：提升产物 `chain.enabled = false`，靠 `lifted` 块里已有的
`source_sha256` 说明它来自哪份原件。**这是诚实的等价物，不是链。**

## 3. 这买到了什么，以及买不到什么

**买到：**

* 链头发布之后的任何改动都留痕（篡改可检测）；
* 「重复 `seq`」（RED-39）与「伪造 `frame_hash`」（RED-41）成为链的特例，两条
  独立检查退化为一条结构性质；
* Phase 4 的外部读者有一件可自行复算的东西：拉仓库、逐行哈希、对上 MANIFEST。

**买不到，必须写进文档而不是让人自己发现：**

1. **链头发布之前的伪造抓不到。** 操作者可以先写一份想要的账本，再发布它的头。
   得到的性质精确地是「**发布之后的篡改可检测**」，不是「记录是真的」。
2. **记录的真实性无法本地证明。** 没有任何东西能证明那些帧真的来自 ARC——只有
   API 签名的回执能做到，而 API 不提供。
3. **对臂没有增量。** 臂本来就写不了账本；这一条从头到尾是关于操作者的。

第 1、2 条如果不写清楚，本提案就会犯 `LEDGER_FORMAT.md` §4 刚犯过的那个错——
那句「过了写入方的账本不可能含有 key」是过度声明，红队 RED-15 当场收账。同一
个错不值得犯第二次。

## 4. 考虑过并否掉的替代方案

| 方案 | 否掉的理由 |
|---|---|
| 什么都不做，只保留 D-024 的诚实陈述 | 是当前状态。可接受到 Phase 4 为止；释出时它会变成论文的一处软肋，而那时再补就没有历史链头可发布了——**链只对它建立之后的记录有效，所以拖延是有成本的，这是本提案最实质的理由。** |
| 逐记录签名（私钥签每条记录） | 操作者持有私钥，威胁模型不变。只有当密钥在别人手上时才有意义，而 Phase 1 全离线。 |
| 只读介质 / 文件系统 append-only 属性 | 依赖操作系统，且操作者是 root。 |
| 外部时间戳服务 / 公证 | 需要联网，Phase 1 刻意离线；可作为 Phase 4 释出前的一次性加固单独考虑。 |
| 把 `prev` 设为必填并升 `v1.1` | 让所有 v1.0 读者报废，惊动三臂与电池，换来的强制力还不如「链头」这一条。 |

## 5. 若通过，工作清单

1. `proxy/ledger.py`：`Ledger` 维护 `_prev`，`append` 写 `prev`；开文件时从末
   行重建，与 `_last_seq` 同一处。
2. `proxy/canon.py`：`prev` 进 `ENVELOPE`，可选。
3. `proxy/tools/verify_chain.py`：按字节逐行校验；接受期望链头；`--head` 输出
   当前链头。
4. `proxy/tools/validate_ledger.py`：`run_start` 声明了链就要求链完整。
5. `proxy/runner.py`：链头进 `run.json`；`runs/*/MANIFEST.json` 收 `ledger_head`。
6. `proxy/scoring/arc_v1.py`：新增一条检查（链完整 / 未声明 / 断裂三态，断裂
   为 FAIL），并按 D-014 配一条伪造对照——改一行中间记录，断言它变红。
7. 文档：`LEDGER_FORMAT.md` 新增一节（含第 3 节那两条买不到的东西）、
   `DECISIONS.md` 新增一条并订正 D-024、`CANON_MIGRATION.md` 补一句提升流不上链。
8. `PARTNER_SYNC` 向 battery 与 baseline-arms 各登记一段：**不需要你们改任何
   东西**，但读者可以据 `run_start.chain` 分辨一条流有没有链。

**建议派工**：`proxy/` 轨道，与「接一臂真跑」同一批——因为第一次真跑的账本正
是第一份值得上链的账本，而在它之前上链是零成本的，在它之后就晚了一天。

## 6. 请监控裁决的三件事

1. **做不做。**
2. **什么时候做**：本提案的意见是「在第一次真跑之前」，理由见上——链对它建立
   之前的记录无效，所以每推迟一轮，就有一轮的账本永远上不了链。
3. **链头的发布位置**是否就用 `runs/*/MANIFEST.json` + git + 远端。若监控认为
   需要更强的见证（例如释出前做一次外部时间戳），那是一个可以叠加的独立决定，
   不影响本提案。

本提案不是指令，本轨道未擅自实施；P-9 分支里只有 D-024 的登记与 STATUS 里那句
「账本完备且自洽，臂写不了它——但操作者可以」。
