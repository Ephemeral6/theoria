## 一、必须先说的：不要做我的建议 1

我建议把 `standing_verdict` 改调 `standing.occupied()`。**别做。** 五个理由，
每一条都足以否掉它：

1. **不确定性的极性是反的。** `occupied()` 在拿不准时返回「未被占用」
   （`standing.py:192-195`，首次见到该 agent 时按设计返回 `None`）。在
   `standing.py` 里这意味着「那就启动一个」——很便宜。搬进 `cmd_sweep` 就变成
   **「那就释放它的认领」**，正是 `fc2097b5` 整个设计围绕着避免的那种不对称。
   **每一处不确定都从安全翻成不安全。**
2. **它不是谓词，是有状态的。** `occupied(agent, state)` 会写 `state`，
   `standing.py:242` 自己注明「只调用一次：它会写状态」。`board.py` 没有状态管道，
   移植过去每次都拿到 `{}`，于是每次都走首次分支，**退化成一条光秃秃的 20 分钟锁门槛**；
   而共用同一个状态文件又会破坏 standing.py 自己的记账。
3. **20 分钟 vs 90 分钟**，而且踩在一个并不可靠的信号上（见下一节）。
4. **它根本没摆脱 mtime。** `standing.py:203` 的 `file_age` 仍然来自
   `getmtime(ops-status/<id>.json)`——那个被 git 跟踪、可被 merge 改写的文件。
   它是**多加了一条腿，不是换掉了那条腿**。
5. **它的生产记录就是答错。** `standing.log` 08:15Z–10:00Z 连续八次
   `skip RES-4: cycle advanced to 16 … hb=205min`，例行程序把自己关了三个多小时
   还在印令人安心的行（`443211dd` 已修）。错的方向是**假占用**——在它自己的极性下
   是安全的，一旦反过来当判死闸门用，就变成**假释放**。

**量化后果**：RES-1 的锁诚实年龄在 10:33Z 约 **162 分钟，超 20 分钟门槛 142 分钟**，

`standing.py:178` 没有下界 ⇒ 它永生。

## 三、标题订正：不是「装饰性」，是「没上膛」（un-armed）

## 四、我把量级说大了

`git merge` **只改写 blob 变了的文件**（对照实验：未变的文件 mtime 连纳秒都没动）。
所以「一次合并就把所有人的判死时钟清零」这句**在一般情况下是假的**。
把 2026-07-29 全部 **99 个** merge 都量一遍：

| 写了几个心跳文件 | merge 数 |
|---|---|
| 0 | **81（82%）** |
| 1 / 4 / 5 | 2 / 1 / 2 |
| 8 | **13** |

99 个里只有 18 个写了任何东西。我原文的「14 次、10 次全中」在数量级上没错、
在 8/8 那一档甚至偏保守，**但我隐去了 99 这个分母**。而且确实存在
**08:45→12:00（195 分钟）** 和 **15:33→18:08（155 分钟）** 两个窗口，
判死时钟跑满了。机制成立，普遍性被我夸大了。

「十二个判活点里十一个从不打开文件」也说松了：`scan.py:498/:643/:858` 会打开，
`scan.py:640-660` 就是专门审 `utc` 的探针。**收窄后仍然成立的那句是：
系统里每一个「年龄」都来自 `getmtime`**，所以一份冲突标记读出来就是 0 分钟 = LIVE。
