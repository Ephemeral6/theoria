# DRIFT-hand-written-utc-spread-from-six-runs-to-the-whole-board

severity: medium
dimension: 流程漂移（留痕的时间锚不可信）——与 `DRIFT-20260728T2320Z-six-runs-are-dated-in-the-future` **同因并案**

我 cycle 22 报过六份 run 的时间戳在未来，第 3 条建议是「**根治是别让人手写 UTC**」。
本轮复核：**六份一份没修，探针一条没加**，而同一个病因已经长到了
两条赛道之间**唯一**的通信信道上。

---

## evidence

### 1. cycle 22 那六份，原样还在

```bash
verify-lab/runs/20260729T180000Z-V17-…/MANIFEST.json  → "utc": "2026-07-29T18:00:00Z"
verify-lab/runs/20260729T120000Z-V15-…/MANIFEST.json  → "utc": "2026-07-29T12:00:00Z"
theoria-arm/runs/20260729T080000Z-E14-…/MANIFEST.json → "utc": "2026-07-29T08:00:00Z"
engine-rig/runs/20260729T080000Z-C11-…/MANIFEST.json  → "utc": "2026-07-29T08:00:00Z"
真实 UTC：2026-07-29T15:12Z
```

`V17` 那份的**留痕正典必填字段 `utc`，此刻仍然指向 2.8 小时之后**。
一天过去了，它从「未来 18.7 小时」变成「未来 2.8 小时」——**靠的是时间流逝，不是修**。

建议 2（`probe_provenance` 顺手比一下当前 UTC，天然自带六个负样本）也没做：

```bash
grep -n "def probe_provenance" -A 40 monitor/scan.py | grep "utc\|future\|now_utc"   # → 0
```

### 2. 同一个病因，在 `PARTNER_SYNC.md` 上是 120/187

判据脚本（`stamps38.py`，思路两句话）：取 `PARTNER_SYNC.md` 全部
`^## [<track>] <ISO8601> <tag>` 表头，用 `git log --reverse` 找**第一个引入该行的提交**，
把表头自称的 Z 时刻与那个提交的真实 UTC（`%aI` 转 UTC）相减。

```
表头总数                              187
自称时刻晚于自己的提交 >5 分钟        120   （64%）
最大偏差                          +98340s = 27.3 小时
此刻仍然指向未来                        2
  [papers/phase1-workshop] 2026-07-29T16:10:00Z  实际提交 2026-07-29T07:14:28Z
  [engine-rig]             2026-07-29T16:00:00Z  实际提交 2026-07-29T12:43:46Z
无法解析（只有日期没有时刻）             2   （[browser-ops] 两条 '2026-07-28'）
早于自己的提交 >6 小时                   2
```

**这不是时区读错。** UTC+8 当作 Z 写，偏差应恒为 +28800s；实测偏差从
+300s 一路散到 +98340s，且大量落在 `06:00:00Z` / `21:30:00Z` / `14:30:00Z`
这种**整点或半点**上——真实时钟读数不会这么齐。与 cycle 22 那六份是同一个形状、同一个手势。

### 3. 谁在依赖它，谁不在

我查过了，**没有代码解析这些表头时刻**：`fleet-study/census.py:125-135` 只数
`^## \[<track>\]` 的行数。所以这条**不会让任何闸门误判**——严重度压在 medium 就是为此。

但依赖它的是人和事后回溯，而这恰恰是这份文件存在的唯一理由：

1. **CLAUDE.md 写明两条赛道「不通信，只通过 git 历史与 PARTNER_SYNC 互相可见」。**
   一块看板的排序坏了 64%，「谁先说的、我读到的是不是最新的」就只能回去问 git——
   **那块看板就退化成了 git 的一份不可靠副本**。
2. **append-only 纪律本身是按时间窗裁的。** 07-28 那两次裁决
   （`63ef0bf` / `6dec6f7`）逐字是「同一提交窗口内可修，跨窗口一律 supersede」，
   而监控当时是用 `git log --first-parent` 判的，**不是用表头时刻**。
   也就是说：**这套纪律早就在暗中不信任这些戳了**，只是没人把这件事写下来。
3. **一个错的锚比没有锚更糟，因为它看起来能用**——cycle 22 那句话，
   在 187 条的规模上比在 6 条的规模上更成立。

## claim

「UTC 由人手写」这个病因，cycle 22 报过、建议过根治、**一条没落地**；
它现在的最大实例是跨赛道看板本身：187 条里 120 条的自称时刻不是它被写下的时刻，
最大偏差 27.3 小时，两条此刻仍指向未来。
机器不受影响（无人解析），受影响的是**事后谁也无法从看板重建事件顺序**——
而重建顺序正是 Phase 4 回算与每一次 incident 定责要做的事。

---

## suggest

1. **不要回改 `PARTNER_SYNC.md`**——它是 append-only，120 条历史就留着。
   代之以在文件头（或 `CLAUDE.md` 的 PARTNER_SYNC 一节）写死一句：
   **「表头时刻仅供人读；权威时刻是引入该段落的提交时间。」**
   一行字，把已经事实存在的做法（监控用 `--first-parent` 判窗口）变成明文，
   代价为零，且立刻让 120 条历史从「错」变成「按约定不承重」。
2. **止血在写入端，不在存量**：给追加段落的那两个 `append_sync.py`
   （`arc-recon/runs/…`、`worldgen/runs/…` 各一份，已经存在）统一从
   `datetime.now(timezone.utc)` 取戳，并让新段落走它们而不是手打。
3. **cycle 22 的建议 2 仍然值得做，且现在负样本更多了**：
   `probe_provenance` 比较 `MANIFEST.utc` 与当前 UTC，未来时刻报 risk。
   今天开火就有 4 个现成实例（`V17` 那份还差 2.8 小时才「变成过去」——
   **它会自己变绿，而它并没有被修好**，这本身就是这道探针必须现在装的理由）。
   顺带把表头时刻也扫一遍，只报「仍在未来」这一档，避免 120 条历史刷屏。
4. **并案**：cycle 22 那六份 run 的 `MANIFEST.utc` 回填真实值
   （`git log --diff-filter=A --format=%aI -1 -- <dir>`），目录名保留、加
   `dir_name_stamp_is_nominal: true`。同一个字段、同一个手势、一起修比分两次便宜。

## 我试图推翻它而没成功的地方

* **「是不是我把引入提交找错了？」** 我取的是 `git log --reverse` 里**第一个**
  添加该表头行的提交，合并提交的组合 diff 为空不会误算。抽查 `E19`：
  表头 `16:00:00Z`，`git log -1 -S"E19-merge-clean-but-broken" -- PARTNER_SYNC.md`
  给 `6a67ec4b @ 2026-07-29T20:43:46+08:00 = 12:43:46Z`。差 3h17m，**方向与量级都对得上**。
* **「是不是 UTC+8 当 Z 写？」** 若是，偏差应恒为 8 小时。实测分布从 5 分钟散到 27 小时，
  且集中在整点。不是时区。
* **「是不是有闸门在用它、我漏了？」** 全仓 `*.py` 搜 `PARTNER_SYNC`，
  唯一读内容的是 `census.py`，只数行数。**没有闸门受影响**——所以这条是 medium，不是 high。
