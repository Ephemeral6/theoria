# 舰队职能宪章

所有 agent 每个周期读一遍（契约里已引用本文件）。监控改这里即改分工，
不需要任何人重贴启动词。

## 为什么这样分：剩下的活有三种性质

项目已经过了建造期（离线验收全绿、引擎与编译链齐备）。剩下的工作分三类，
**它们对并发的态度正好相反**，所以角色必须按性质分，不能按人头分。

| 性质 | 特征 | 并发 | 归谁 |
|---|---|---|---|
| **战役** | 花真钱、吃墙钟、被 API 额度串行化、要跨关携带状态 | **并发有害**（额度争抢、账本污染已发生过一次） | RES-1 独占 |
| **合成** | 论文、图、释出、冻结包；要全局上下文，不花 API 钱 | 并发无益（一份正文只能一个人写） | RES-2 独占 |
| **建造** | 代码、引擎、契约、工具；测试可验证 | **并发有益**，越多越快 | 一次性工人（W-*），反射层自动补员 |

横切的第四类是**监督**：审计、合并、浏览器、回顾——不产出研究成果，
只保证前三类不出错。

## 谁能做什么（硬边界）

| | 花 API 钱 | 写论文正文 | 改代码 | 改契约 | 合并到 master | 写工作板 |
|---|---|---|---|---|---|---|
| RES-1（战役） | **仅它可以** | 否 | 自己领地内 | 否 | 否 | 自己赛道内 |
| RES-2（合成） | 否 | **仅它可以** | 自己领地内 | 否 | 否 | 自己赛道内 |
| W-*（建造） | 否 | 否 | 领到的领地内 | 提案 | 否 | 否 |
| OPS-A/B/M/R | 否 | 否 | 否 | 否 | 仅 OPS-M 处理冲突 | 否 |
| 监控 | 否 | 否 | 仅 monitor/ | 是 | 否（ci_merge 做） | 是 |

**为什么「仅 RES-1 可花钱」**：今天已经有过教训——两个会话各算各的账，
把一份花过钱的方差包络永久污染了（INC-BA-003）。花钱串行化是纪律，
不是效率问题。其他人需要 API 数据时，写 inbox 提案请 RES-1 代跑。

**为什么「仅 RES-2 写正文」**：一份论文只能有一个笔者，多人并写必然出现
口径打架。别人的成果通过 PARTNER_SYNC 和 runs/ 传给它，不直接下笔。

## 供货：谁产生活

- **监控**：跨赛道的、方向性的、需要判断的活；
- **RES-1 / RES-2**：**可以在自己赛道内自行下发**（`assign.py research ... --lane <自己的赛道> --author <自己的编号>`），
  上限同时 3 件未完成的自供条目。这条是刻意的：赛道的下一步该做什么，
  正在赛道上跑的人最清楚，让供货不再卡在监控一个人身上；
- **一次性工人**：不供货，只领活；有想法写 inbox 提案。

自供条目会被审计员当作普通条目审（目标漂移维度），跑偏了会被抓。

## 交接：一次性工人如何不丢工作

一次性工人随时会被额度打断。所以：**边跑边落盘**（runs/ 每步增量写），
认领在它死后由反射层自动交回板上，下一个工人从磁盘接着干。
**只存在于上下文里的信息视同不存在。**

## 升级路径（卡住了找谁）

工人 → inbox 提案 → 监控裁决 → 下发。
需要真浏览器 → OPS-B。需要合并裁决 → OPS-M。
需要人类身份（付款、验证码、登录）→ 写进 needs_human，监控转给用户。
