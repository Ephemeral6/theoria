## Core commitment

I predict **genuine cascade**: ACTION2's 7 frames are 7 different world states,
an animation/settling sequence played out by one command. I predict the 7-frame
batch is a property of **ACTION2 in this game**, not of the particular state, so
the second and third ACTION2 also return 7. I predict actions 3/4/5 behave like
ACTION1 did — single-frame responses — because a 1-frame response is what this
game gave for both of the non-ACTION2 commands observed so far.

I also predict the batch does **not** re-send the pre-action state as its first
element: `first_equals_prev_last` will be `False` on every cascade batch. The list
is "what happened after the command", not "where we were plus what happened".

## What would decide it, and what would surprise me

The observation that settles `action -> frame SEQUENCE` versus `action -> single
frame, the list being just a container` is `intra_batch_changes` on the 7-frame
ACTION2 batches. If it is 6 (or any value > 0) with `distinct_frames > 1`, one
command produced several genuinely different world states and the batch is a
trajectory: a single-frame model (A0's D-A0-004) silently discards the
intermediate states, and a rule miner fed only the last frame would be mining
across a gap of up to six unobserved transitions. If instead `distinct_frames == 1`
and `intra_batch_changes == 0`, the 7 entries are 7 copies of one grid — padding,
the list is a container, and D-A0-004 survives untouched. A third, weaker reading
would be `distinct_frames == 2` with `intra_batch_changes == 1`: a before/after
pair padded out to 7, which is a *container with a boundary*, not a cascade; that
would still leave a single-frame model mostly defensible.

What would surprise me: (a) `distinct_frames == 1` on ACTION2 — I have committed
to a real cascade and would be plainly wrong; (b) ACTION3/4/5 returning 7 frames,
which would mean the cascade is a property of the *state* (or of every non-no-op
action) rather than of ACTION2, and would make my "ACTION2 is special" reading
wrong; (c) `first_equals_prev_last == True` on a cascade batch, meaning the batch
re-sends the pre-action state and the true number of new states is 6, not 7;
(d) the second ACTION2 returning a count other than 7 — most sharply, a *shorter*
batch, which would mean the cascade length is driven by how much of the board is
still in motion and is therefore state-dependent; (e) any non-200, especially on
ACTION3/4/5, which the precheck never reached for this game.

**What I got right.** The core commitment: this is a genuine cascade. Every
multi-frame batch (5 of them) has internal change; **zero** are all-identical.
The prefix reproduced the precheck exactly — the same three batch hashes across a
different session on a different day, so the game is deterministic from RESET and
there is no cross-session residue in this prefix. ACTION1 is confirmed an accepted
no-op (identical frame hash `f79ab0e9d856fdf8` to RESET). Shapes constant, state
constant, no failures.

**What I got wrong, and it is the more interesting half.**

1. *"The 7-frame batch is a property of ACTION2."* Wrong. ACTION4 returned 7,
   ACTION5 returned 17. Cascades are a property of the game, not of one action.
   ACTION3 returned a single changed frame, so it is also not "every action".
2. *"ACTION2 always returns exactly 7."* Wrong. The third ACTION2, from a state
   reached via 3/4/5, returned **9**. Batch length is state-dependent, not a
   per-action constant — the (d) surprise I named, except it came out longer
   rather than shorter.
3. *`first_equals_prev_last` is `False` everywhere.* Wrong, and inconsistently so:
   `True` on steps 3, 5, 7; `False` on steps 2, 4, 6. So the batch **sometimes**
   opens with the pre-action state and sometimes does not. Where it is `True`, the
   number of genuinely new states is n−1, not n. I had committed to a single rule
   and there is no single rule — at least none I can read off 8 steps.
4. *Padding and cascade are exclusive.* Wrong, and this is the finding I did not
   anticipate at all. ACTION5's 17 frames are
   `A A A A B B B B C C C C D E F G H`: three runs of four identical frames
   followed by five singletons — `distinct = 8`, `changes = 7`. The same response
   contains both real intermediate states *and* literal repetition. Any consumer
   that dedupes a batch is throwing away timing; any consumer that treats every
   frame as a distinct transition is inventing 9 transitions that never happened.

**Consequence for D-A0-004.** "action → single frame" is not defensible for this
game. One command produced up to 8 distinct world states, and the last-frame-only
model would hide 7 transitions behind a single edge. A rule miner fed only the
final frame of step 6 would have to explain a 17-tick change as one step.
