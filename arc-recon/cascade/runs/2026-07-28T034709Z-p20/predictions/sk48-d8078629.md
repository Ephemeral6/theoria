## What would decide it, and what would surprise me

The whole verdict hangs on `distinct_frames` for the seven 2-frame batches. If
`distinct_frames == 2` and `intra_batch_changes == 1` on essentially every
action, the step is `action -> frame SEQUENCE`: one command drove the world
through an intermediate state that a single-frame model silently discards, and
D-A0-004 ("action -> single frame") is throwing away exactly the transitions a
rule miner needs — the intermediate is where the mechanism is visible. If
instead `distinct_frames == 1` and `intra_batch_changes == 0` everywhere, the
list is a container: two copies of one grid, the batch hash differing between
steps only because the underlying single state advanced, and D-A0-004 survives
untouched. A third, more interesting outcome would be `distinct_frames == 2`
*with* `first_equals_prev_last == true` — that would mean the batch is
`[old_state, new_state]`, i.e. a redundant echo rather than a cascade, and the
"sequence" would carry no state the single-frame model lacks. I predict the
first. What would genuinely surprise me: (a) a frame count other than 2 on any
action — sk48 gave exactly 2 on all 8 precheck actions across two sessions, so a
1 or a 3 would mean the batch length is state-dependent in a way the precheck
never saw; (b) any batch-hash mismatch against `run_a`, since two independent
precheck sessions already agreed at all 9 positions, so a mismatch would mean
either genuine cross-session residue that the precheck's own residue check
missed, or drift on the server since 2026-07-27T18:31Z; (c) `first_equals_prev_last`
coming back true, which would demote the whole result from cascade to echo.

### One thing I did not predict, from the individual frame hashes

The per-frame hashes show structure the batch hashes could not:

```
seq 0 RESET    e4bbd31c…
seq 1 ACTION1  2d581983…  c40f8708…
seq 2 ACTION2  2d581983…  e4bbd31c…      <- ends back at the RESET frame
seq 3 ACTION3  58358a8d…  7a6fc2a4…
seq 4 ACTION4  c5bb8bf4…  8ccbe276…
seq 5 ACTION1  def8a292…  2d4043f4…
seq 6 ACTION2  def8a292…  8ccbe276…      <- ends back at seq 4's final frame
seq 7 ACTION3  0cbf8446…  3bf51d2f…
```

Two regularities I had not committed to. (i) ACTION2 undoes ACTION1: seq 2 ends
on the RESET frame, seq 6 ends on seq 4's final frame. A1/A2 look like opposite
moves. (ii) The *first* frame of a batch is shared between A1 and A2 issued from
the same state (`2d581983…` at seq 1 and 2; `def8a292…` at seq 5 and 6) while
their second frames differ. So the first frame is an intermediate that depends on
the starting state and not (or not only) on which of those two actions was sent —
it is not the pre-action state (`first_equals_prev_last` is false everywhere) and
not the post-action state either. That intermediate is exactly the state a
single-frame model deletes.
