## 2 · Crux: false certificate, or true statement about a different problem?

This is the bullet that decides the item. I ran the decisive experiment rather
than argue it (`recompute.py`): for all 2422 held-out cases, BFS the goal from the
start over the **complete** move set *and* over the **reduced** move set the
engine was handed.

```
certificates                             1408
FALSE vs BFS over COMPLETE move set        58  (4.1 %)
FALSE vs BFS over REDUCED move set          0   <-- the handed system
```

**Every one of the 1408 certificates, including all 58, is a true statement about
the transition system the engine was handed.** That is not a lucky measurement —
it is the pagoda soundness theorem: `inv_init ∧ inv_closed(M) ∧ goal_break`
entails unreachability in the transition system generated by `M`, for any `M`.
Withholding a geometry changes `M`, so it changes the problem, not the truth
value of the argument. The 0/1408 is the empirical confirmation.

### Does the certificate's own text, schema, or consuming code assert something about the *game*?

Mixed, and this is the whole of the real finding.

*Scoped correctly (the payload does disclose its own quantifier):*

* `payload["move_instances"]` publishes the exact list quantified over — for the
  witness, `['jump(0,1,2)', 'jump(1,2,3)', 'jump(2,1,0)']`, three of four.
* `payload["premise_check"]` publishes `missing_moves`, `move_list_complete`,
  `moves_raising_potential`.
* `LpOutcome.as_json()["scope_of_claim"]` (`potential.py:246-249`) states the box.
* `CONTRACTS/candidates_schema.md` is thin but decisive on adjudication:
  `status` is **always** `"candidate"`, and the file says outright
  「status 字段永远是 "candidate"——引擎不裁决，裁决是 theorize(LLM) 的事」. The
  stream is a proposal stream. Nothing on it is a verdict about the game.

*Unscoped (reads as a claim about the game):*

* `payload["claim"] = "goal unreachable from 0011"` (`potential.py:174`) — no
  mention of a move list.
* `payload["rendering"]`: *"every **legal** move leaves it non-increasing"*
  (`potential.py:175-178`) — "legal" reads as legal-in-the-world.
* `payload["holds"] = True` (`potential.py:172`) — an unqualified verdict field.
* `engines/lp_potential/README.md`: *"no configuration ever gets a certificate
  unless the enumeration agrees it is unsolvable"* — a world-level assertion.
* `CLAUDE.md`'s standing caveat: *"It never certifies a solvable configuration"* —
  unquantified. Under the correct scoping ("solvable in the handed system") it is
  true 1408/1408; under the naive reading it has 58 counterexamples.
* `premises_against_graph`'s own docstring (`potential.py:583`) says a dropped
  move means *"the claim is simply false"*, and
  `tests/test_lp_potential.py:203` calls such a certificate *"still wrong about
  the world"*. The repo's prose asserts the world-level reading in places.

### `sound_over_graph` — checked, and it is *not* the engine disclaiming

The parent's hypothesis is wrong in an interesting way. `sound_over_graph` is not
a disclaimer; on the production path it is a **tautology**:
`solve_certificate` derives `certificate.moves` from `graph` via
`moves_from_graph`, and `check_exactly` has already proved every listed move
non-increasing — so `premises_against_graph(cert, graph)` on that *same* graph
necessarily returns `missing_moves: []` and `moves_raising_potential: []`. The
engine's own docstring concedes it: *"Production cannot reach either branch"*
(`__init__.py:57-59`). Measured: **1408 / 1408 certificates pass the gate on
their own graph** (`recompute.txt`, `emitted when gated on the REDUCED graph
1408`), 0 / 1408 pass it against the complete graph. It is a self-consistency
check wearing the name of a soundness check, and it carries zero bits for the
caller who produced the certificate.

**No consumer honours it.** Repo-wide grep for `sound_over_graph` and
`premise_check`: the only *readers* are
`engines/lp_potential/__init__.py:65,92` (the engine's own gate) and
`tests/test_lp_potential.py:361,365`. Every other hit is a string in a
Markdown/report file or a one-off script inside E16/E17. Nothing downstream —
not the arm, not the theory-compiler, not `tools/validate_candidates.py` —
reads either field. So the disclosure exists and is unread.

### Judgement

**This is a caller/contract-scoping defect, not an engine soundness defect** —
with one genuine artefact defect attached.

The engine's mathematical output is sound and its scope is fully disclosed in the
payload (`move_instances`, `premise_check`). It has no channel to the world other
than the `graph` argument, so "is this move list complete for the game?" is a
question it structurally cannot ask, and D-035 already localises soundness to
*"the completeness of the enumeration, not the arithmetic."* Assembling a
complete move list is the caller's obligation. What is genuinely defective is
(a) three headline strings (`claim`, `rendering`, `holds`) and `CLAUDE.md`'s
caveat that are unquantified over that obligation, and (b) `sound_over_graph`,
whose name promises a soundness assurance it cannot give and which no consumer
reads anyway.

The reported claim 2 — *"soundness holds only over the move list the engine is
handed"* — is **literally true and is the correct statement of the soundness
theorem**, not a refutation of it. Reporting it as an engine-soundness finding
overstates it.

**NARROWER-THAN-CLAIMED** (as an engine-soundness finding: **REFUTED**; as a
claim-scoping and field-naming defect: **ESTABLISHED**)

## 4 · Point 5 — "the arm is a partial-evidence caller by construction"

Refuted on the load-bearing half. **No code path in `theoria-arm/` reaches
`lp_potential` at all, and none can today.**

* `theoria-arm/world/adapt.py:352-358`, `run_engines`, is the dispatch step.
  `dispatched = ["mdl_segmenter", "cegis_miner", "zero_space"]`. `lp_potential`
  is in the `not_dispatched` dict with the reason recorded in the artefact:
  *"needs an explicit state graph with enumerated moves; none exists for a 64x64
  world whose dynamics are unknown."*
* Repo-wide grep for every call site of `lp_potential.run` / `.candidates` /
  `.decide` / `solve_certificate`: **zero outside `engine-rig/` and `fuzzlab/`.**
  Nothing in `theoria-arm/inner/` (`plan.py` imports `fd_adapter`; `probe.py`
  imports `probe_frontier`; `certify.py`, `books.py`, `grammar_card.py` mention
  `lp_potential` only in refusal messages).
* `theoria-arm/_bootstrap.py`'s `UPSTREAM_PINS` — the files the arm's results
  depend on — pins `mdl_segmenter`, `cegis_miner`, `zero_space`,
  `probe_frontier`. **`lp_potential` is not pinned.** The arm does not depend on
  it.
* The three arm candidate streams under `theoria-arm/runs/*/candidates.jsonl`
  contain only `mdl_segmenter` and `zero_space` rows. Zero `lp_potential` rows
  have ever been produced by the arm.
* The one place the arm would consume a pagoda certificate — `gen_lean`'s pagoda
  development (`inner/books.py:238-258`) — is not attempted and records why:
  *"needs a LINE world plus an lp_potential certificate; this is a grid world
  with no state graph."* `certify.expensive` reports `available: false`.

So nothing downstream treats an `lp_potential` certificate as a statement about
the game, because no such certificate is ever produced outside `engine-rig/` and
`fuzzlab/`, and `fuzzlab/worlds/jumpgraph.py` builds complete graphs.

What survives: *if* the arm were ever wired to build a state graph from its own
learned rules, it would be a partial-evidence caller, and the hazard in §2 would
become live. That is a real forward-looking risk about a code path that does not
exist. Stating it in the present tense — "the arm is a partial-evidence caller by
construction" — is false today.

**REFUTED** as stated; the conditional form ("would be, if wired") is
**ESTABLISHED** as a design risk.

## 6 · Point 6 — the `bound=10` box and the missing Farkas dual

Both true, one narrower than stated.

* `no_linear_pagoda` is HiGHS float infeasibility inside `|w_i| <= bound`, and
  the engine says so at length: `potential.py:71-76`
  (`STATUS_MEANINGS[NO_LINEAR_PAGODA]` — *"no exact rational infeasibility
  certificate (Farkas dual) is produced, so this is the solver's verdict, not a
  proof of non-existence"*), `potential.py:212-226`, `potential.py:282-289`, and
  `scope_of_claim` on every emitted outcome row. This hedge is in the **payload**,
  not only in Markdown.
* **"Hard-coded" is too strong.** `bound` is a keyword parameter with default 10
  on `solve` and `decide`, and it travels on `LpOutcome`. It is *not* exposed on
  `run(...)` — signature confirmed — so the emit path is fixed at 10. Accurate
  wording: *default 10, overridable on `solve`/`decide`, not overridable on
  `run`.*
* The 638: E11 §6 rebuilt the LP for all 639 silences —
  639/639 infeasible at `bound=10`, **638** still infeasible at
  `bound = 100 / 10⁴ / 10⁶`, so exactly **1** silence is the box rather than the
  mathematics, and 1 of the 1550 issued certificates sits at `|w| = 10`.

**ESTABLISHED**, with "hard-coded" **NARROWER-THAN-CLAIMED**.

## What I would and would not put in a frozen document
