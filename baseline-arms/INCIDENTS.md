## INC-BA-001 — 封存堆污染：上游 Schema artifacts 的检索过程本身泄露了封存局机制

* **严重度**：blocking（对受影响的封存局）
* **时间**：2026-07-28
* **阶段**：M3，定位 Schema（Feng et al.）官方发布物
* **本轨道对 ARC API 的封存局调用次数**：仍为 **0**。本事件不涉及任何游戏调用。

### 发生了什么

M3 的任务是「在仓库里、或按 Theoria.md 的引用线索，定位官方发布的 Schema 代码
仓库或 artifacts」。`Theoria.md` 里**没有任何引用**（无 arXiv id、无 URL、无参考
文献节——已 grep 确认），所以只能公网检索。检索被派给一个子代理执行，并**预先
给了它明确的封存堆约束**：只报发布物的位置与可用性，不得读取、总结或转述任何
单局机制。

子代理照做了——它没有向本轨道转述任何机制内容——但它报告：**Schema 的项目主页
把游戏内容放在很靠前的位置，在它意识到并停止阅读之前，页面正文已经描述了若干
封存局的机制。**

### 受影响的封存局（按子代理自报的泄露程度）

| game_id | 堆 | 泄露程度（子代理自评） |
|---|---|---|

| `ft09-0d8bbf25` | **封存** | 实质泄露——明确点名该局的隐藏机制 |
| `re86-8af5384d` | 封存 | 轻微（证据卡片说明文字，多为动作数） |

| `sb26-7fbdac44` | 封存 | 轻微 |
| `bp35-0a0ad940` | 封存 | 可忽略（仅来自 HF 文件名列表） |

`dc22-fdcac232` 需要特别注意：`Theoria.md:416` 把 DC22 指定为图 5 的案例展品。

### 泄露的边界（重要）

* 污染的是**该子代理的上下文**。它明确声明未向本轨道转述任何机制内容，
  本轨道主上下文中**没有**任何封存局的机制信息——只有「哪几局被污染了」这份清单。
* 该子代理的上下文**对任何封存局工作都不再安全**，不得复用。
* 本轨道**不会**打开 `schema-harness.github.io` 或该 HF 数据集。

### 为什么没能事先避免

约束给了、也被遵守了，但它防不住这一类：**判断一个页面是否安全，需要先读它。**
预防措施只能是「不去读」，而 M3 的任务恰恰是「去找」。这是任务本身自带的张力，
不是执行失误。

### 建议处置（归 `arc-recon` 与人工决定，本轨道不代劳）

1. 把上述 9 局在 `contamination_register` 里从 `never_audited` 上调；
   `ls20` 与 `ft09` 至少到 `trajectories_reviewed` 一级。
2. **切分不要改**（`piles.json` rules 第 3 条：开局后改动即事故）。受影响的局
   应作为「已污染的封存局」单独标注，而不是搬进开发堆。
3. 考卷子集（`Theoria.md:372` 的 ⟨m⟩ 局）选点时避开这 9 局，尤其 `ls20`/`ft09`。
4. 若 `dc22` 仍要当图 5 展品，需说明其污染等级。

### 制度性后果，应写进纪律

**上游 Schema artifacts 是一个「读了就全污染」的物件。** HF 数据集
`schema-harness/arc-agi-3-schema-traces` 的结构是每局一个目录、目录名含 game_id，
两套共 50 个轨迹，**覆盖 piles.json 里全部 25 局**，每个目录里有该局的
`world_model_v*.py` 与 `notes.md`。按 `piles.json` rule 2，读封存局的这些文件
**比玩那一局更糟**——它直接给出机制的成品答案。

可行的安全用法只有一种：**按目录名精确挑出开发堆 4 局，只下载那 4 个目录**，
其余一律不碰。`Theoria.md:311` 正是这么规定的（「上游 artifacts 中属于开发堆的局」）。
本轨道**没有**执行任何下载——那属于预算闸门之后的工作。

**后续**：P-7 已执行路 A，守卫按本条的要求写成正向白名单。见 `SCHEMA_PATH_A.md`。

## INC-BA-003 — 两个会话在同一轨道上并发开跑两场战役，共用一个预算与一份 ARC 配额，彼此互不知情

*（原编为 `INC-BA-002`，与另一会话同时新增的条目撞号，已改编为 003。见文首说明。）*

* **严重度**：high（预算与配额，非污染）
* **时间**：2026-07-28 02:21–02:23 UTC+8
* **本轨道对封存堆的调用次数**：仍为 **0**。两场战役都只跑开发堆，`assert_playable()` 在两边都生效。

### 发生了什么

本会话（P-7，方差包络）在 **02:21:25** 启动 `harness.run_campaign --game ar25-0c556536`。
**85 秒后**，另一个 Claude Code 会话在**同一目录**启动了四个进程：

```
02:22:50  python -m harness.campaign --game ar25-0c556536     (PID 36500)
02:22:50  python -m harness.campaign --game g50t-5849a774     (PID 32604)
02:22:50  python -m harness.campaign --game sk48-d8078629     (PID 33644)
02:22:50  python -m harness.campaign --game tn36-ef4dde99     (PID  7740)
```

`harness/campaign.py`（**非本会话所写**，02:22:16 落盘）自述为
「approved full run: bare CC, haiku tier only, whole development pile」，
口径是 `BUDGET_REPORT.md` §3.4 的 S1：**3014 个成功动作、约 $103、约 46 小时串行
（四进程约 16 小时）**。同一分钟里还出现了 `campaign_status.py`、`merge_ledger.py`，
以及对 `harness/ledger.py` 的一次改写（引入 `BASELINE_ARMS_SHARD` 分片写入）。

两场战役都是**正当的**，各自对着自己的工单：对方跑 S1 全量曲线，本会话跑
`Theoria.md` Phase 3 经济要的**方差包络**（同一格重复 2–3 次）。对方的跑法**产不出**
方差包络（每局只有一条 episode 链，无重复格）；本会话的跑法**产不出** S1 曲线。
两者不重复。**事故不在任何一方跑错，而在于没有任何一方的闸门看得见另一方的花费。**

### 为什么这是事故而不是巧合

三处共享资源，三处都没有共同闸门：

| 资源 | 对方口径 | 本会话口径 | 合并后 |
|---|---|---|---|
| 美元 | $103（止损上界 $164.9：`CEILING_FACTOR 1.6`） | 上限 $50（G1） | **最坏 $214.9** |
| ARC 动作配额 | ~21,430 次 HTTP | ~2,600 次 HTTP | ~24,000 次 |
| `ledger.jsonl` | 分片写 `out/shards/` | 直写 `ledger.jsonl` | 见下 |

配额那一栏是真正危险的一栏。`BUDGET_REPORT.md` §4 早就写明：ARC 侧失败的 400
是否计入配额**未知**，乐观与悲观口径差 **9.7 倍**，并明确建议「批准全量之前应当
先问清 ARC 侧的配额口径，否则可能在毫无预警的情况下烧穿配额」。
两场并发战役正是烧穿它的标准姿势——而且**没有任何一方会看到自己烧穿了**，
因为两边的计数器各算各的。

### 账本层面的具体隐患

对方改写的 `ledger.py` 让 `LEDGER_PATH` 在 import 时按 `BASELINE_ARMS_SHARD`
解析：设了环境变量就写 `out/shards/ledger.<shard>.jsonl`，没设就写
`ledger.jsonl`。本会话的 ar25 进程（PID 11428）在改写**之前**就已 import，
仍直写 `ledger.jsonl`。因此：

* 现状是安全的——两边写的不是同一个文件，没有交错风险；
* 但 `merge_ledger.py` 会把分片并回 `ledger.jsonl`，**若在本会话仍在直写时并入，
  就会与本会话的 append 交错**，而 append-only 账本事后无法修复。

本会话的处置：**后续每局都设 `BASELINE_ARMS_SHARD`**，让本会话的记录也进分片，
分片名前缀 `variance-`，与对方的 `<game>` 分片天然不撞。ar25 那一局的记录留在
`ledger.jsonl` 里，在审计中单独标注其归属，不追改（append-only）。

### 本会话为什么继续跑而不是停

不是「冲动再跑一局」，理由逐条：

1. **增量小且封顶**：本会话的全部计划开销约 $12、约 2,600 次 HTTP，
   是在飞行中那场战役的约 12%；且 G1 硬顶 $50 会先于任何失控生效。
2. **它交付的东西对方产不出**：`Theoria.md` Phase 4 冻结清单里的
   「每格重复数 ⟨n⟩ 由开发堆方差在冻结前定」，只有重复格能定。
   停掉本会话，这个数字仍然没有依据。
3. **停掉不省钱**：大头是对方那 $103，本会话停跑并不改变它。
4. **不可撤销的那一类损害为零**：两场战役都只碰开发堆，封存堆守卫在两边都在。
   钱可以再要，配额可以再申请，封存局烧了就没了——而没有任何封存局被碰。

代价必须写下来：**本会话的方差包络是在对方四进程负载之下测得的**，
其 `http/动作` 与墙钟含并发争用成分，不能与 M4 试点的单价直接比较。
这一条在 `BUDGET_REPORT.md` §10 与 `STATUS.md` 中作为已知偏差登记。

### 本会话没有做的事（明确记下）

* **没有杀掉对方的任何进程**。那是别的会话在飞行中的工作，
  终止它会毁掉已经花掉的钱且产不出数据。
* **没有修改对方的任何文件**——`campaign.py`、`campaign_status.py`、
  `merge_ledger.py`、`out/campaign/` 一律只读。
* **没有改动 `piles.json` 或任何切分文件。**

### 建议处置（归人工，本会话不代决）

1. **给本轨道设一个跨会话的共同闸门**：闸门状态必须落在一个共享文件上
   （例如 `out/campaign_gate.json` 由所有战役进程共同读写并累计），
   而不是各自进程内的计数器。当前两套闸门互不可见，这是本事故的根因。
2. **问清 ARC 配额口径**（`BUDGET_REPORT.md` §4 已提，此处升级为阻塞项）。
   在两场战役并发的情况下，9.7 倍的不确定性不再是可以带着走的风险。
3. 决定这两场战役是否都该跑完。若要砍，建议砍 S1 全量那场（$103，46 小时，
   且其结论——「裸 CC 在基线动作数内过不了关」——试点已给出强指示），
   保留方差包络那场（$12，产出 Phase 4 冻结所需的 ⟨n⟩）。**本会话不自行执行此项**：
   那是对方会话的工作，不归本会话处置。

## INC-BA-002 — 更正：H-A「短 ID 可用」的结论只看了状态码，经帧内容检验为伪

* **严重度**：process（更正已发布的结论）
* **时间**：2026-07-27T18:46Z
* **发现方**：`arc-recon` 轨道（本条为跨轨道确认，证据在其账本）

`AUDIT.md` §6.2 与 PARTNER_SYNC 2026-07-28 段落记录 H-A（ACTION 传 `sk48` 而非
`sk48-d8078629`）「**200 成功**」。该判定只依据 HTTP 状态码。arc-recon 预检期间
对帧内容复核发现：**短 ID 的 200 响应携带的是原始初始帧**（g50t 上 6/6，
哈希恒为初始帧、`n_frames=1`、`levels_completed=0`，与会话真实进度无关）——
即短 ID 的 200 并非作用于活会话的已执行动作，把它当真会污染轨迹。
本轨道自己的 probe log 里就有旁证：`confirm short-id` 一节中不存在的动作
`ACTION7` 也在短 ID 下返回过 200。

**处置**：
1. H-A 的结论降级为「短 ID 会返回 200，但该 200 是伪响应」；
   §6 的总结论（决定性因素是重试）**不变**，且 H-C 与实跑证据不受影响。
2. 幸运的是 `bare_cc.py` / `run_pilot.py` 一直用全 ID 调用，**试点数据不受污染**。
3. 本轨道后续任何 harness 禁止在请求体中使用短 ID；短↔全映射见
   `arc-recon/data/precheck.json` 的 `id_map`。
4. arc-recon 侧的正式记录：其 `incidents.jsonl` INC-005。

教训与 INC-003 / D-006 同源：**状态码不是证据，内容才是。**
