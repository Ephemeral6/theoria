# baseline-arms — 设计决策与理由

只记有理由的选择。纯样板不记。

---

## D-001 模型调用走 `claude -p` 无头 CLI，不走 Anthropic SDK

**决策**：所有裸 CC 臂的模型调用通过 `claude -p <prompt> --model <id>
--output-format json` 子进程发出。

**理由**：
1. 环境里的 `ANTHROPIC_API_KEY` 对 `api.anthropic.com` 直接返回 401
   （它是 harness 宿主凭据，不是裸 API key）。SDK 直连**在本环境不可能**。
2. 更重要的是这在语义上才对。工单要的是「裸 Claude Code」这一列，
   `claude -p` 就是裸 Claude Code 本身；用 SDK 手写一个 agent loop 去
   「模拟裸 CC」反而引入了我自己的 harness 偏差，可比性更差。
3. `--output-format json` 直接回传 `usage`（含 cache 读写分项）与
   `total_cost_usd`，正好是主表和预算报告要的两个量，无需自己估价。

**代价**：每次调用有约 2–4 秒进程启动开销，且 opus/sonnet 每次注入约 2690
input tokens 的系统提示（haiku 只有 10）。这个固定开销必须按档实测，
不能跨档外推——已写进 `AUDIT.md` §4.4 与预算报告。

## D-002 模型 id 一律写全，禁止用 `haiku`/`sonnet`/`opus` 别名

**决策**：矩阵固定为 `claude-haiku-4-5-20251001` / `claude-sonnet-5` /
`claude-opus-5`，配置里写全 id。

**理由**：环境里 `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` 四个变量全部
指向 `Vendor2/Claude-4.5-Opus`，实测 404。用别名会静默跑到一个不存在的模型上，
或者三档全部塌缩成同一个模型——那样跑出来的「跨模型基线」是假的。
写全 id 让这个失败模式不可能发生。

---

## D-003 `ledger.jsonl` 只有两种记录形状，诊断另落 `probe_log.jsonl`

**决策**：`ledger.jsonl` 严格只含工单规定的 `env_step` 与 `model_call` 两种形状；
API 探测、重试统计、viability 判定等一律写 `probe_log.jsonl`。

**理由**：`/arc-gateway/` 尚未存在，本轨道的账本将来要与它的产出**合并**。
如果我往 ledger 里塞第三种自定义形状，合并时要么污染对方的解析器，要么需要
一次过滤重写——而账本是 append-only，事后重写正是本项目要避免的事。
两个文件的代价是零，混一个文件的代价是未来的一次数据迁移。

`probe_log.jsonl` 的 HTTP 层字段名与 `<redacted>` 约定**照抄**
`arc-recon/data/recon_ledger.jsonl`，两者可直接拼接。

## D-004 封存堆纪律写成守卫代码，不写成注意事项

**决策**：`harness/arc_client.py` 在 import 时读 `piles.json`，
`assert_playable()` 在**打开 socket 之前**对封存局抛 `SealedGameError`；
前缀匹配（`sk48` 与 `sk48-d8078629` 同等对待）。

**理由**：封存堆的伤害是**不可撤销**的——一次成功的 RESET 就返回首帧，
那一局对未来的考卷就废了。不可撤销的错误不能靠「记得别这么做」来防。
前缀匹配是因为调用方很容易漏掉版本后缀，而漏掉后缀的 id 一样能打通 API
（见 `AUDIT.md` §6.2 的 H-A）。

本轨道**只读** `piles.json`，绝不写：改动切分文件在开局后即事故
（`piles.json` 的 `rules` 第 3 条）。

## D-005 对 `400 "game not found"` 重试，而不是判定为终止错误

**决策**：ACTION 与 RESET 遇到 400 一律按**瞬时故障**处理，线性退避重试
（默认上限 8 次）；连续耗尽才算该步失败。

**理由**：`INC-002` 把这个 400 判成了终止错误，进而得出「整个在线 API 路线
受阻」。本轨道独立复核（`AUDIT.md` §6）证明它是瞬时的：同一 guid、同一请求体，
重试后返回 200，且能连续推进 11/15 步。最可能的机制是多实例后端里只有部分
实例持有该会话。

**代价与必须记账的量**：平均 **5.07 次 HTTP 调用换 1 次成功动作**。
这个 5× 放大对 ARC 动作配额是否也放大**尚不确定**（失败的 400 是否计入配额
未知），预算报告按「HTTP 次数放大 5×、配额消耗按成功动作数计」给出主估算，
并单列「若失败也计费」的悲观上界。

## D-006 重试失败的步不伪造，如实记为失败步

**决策**：一步耗尽重试后，仍写一条 `env_step`，但 `frame` 为 `null` 并带
`"failed": true` 与失败原因；不跳过、不回填、不用上一帧顶替。

**理由**：账本的价值全在于它是完整的。跳过失败步会让「动作数」这个主表指标
偏小；用上一帧顶替会让轨迹看起来连续、实则伪造。`INC-003` 的教训恰恰是
「一个不会失败的检查不是检查」——同理，一本不会记录失败的账不是账。

---

## D-007 试点范围：4 局 × 3 模型，但受 API 可用性约束

**决策**：试点目标为开发堆全部 4 局 × 3 个模型档位。若某局 RESET 在合理
尝试次数内始终不开窗（`ar25`、`tn36` 目前如此），如实记为「无法开局」，
**不替换成别的局，尤其不碰封存堆**。

**理由**：工单要 3–5 局，开发堆总共只有 4 局，全取即可。样本不足时正确的
反应是报告样本不足，不是去封存堆里找补——那是本项目最贵的一种错误。

---

## D-008 每局设动作上限；试点用 20，全量用官方基线动作数

**决策**：动作上限硬编码在 `run_pilot.py` 里而不是随手传参。
试点 = **每格 20 个动作**；将来全量 = `min(60, baseline_actions[0])`
（不超过该局第一关的官方基线动作数）。

**理由**：裸 CC 在一局上可以无限徘徊，而这是本项目「最容易失控的开销来源」。
试点的目的不是拿结果，是**买一个单价**——够外推就行，多一步都不要。
20 步足够给出每步成本与每步 HTTP 放大率的稳定估计。
全量用官方基线动作数作上限是有客观依据的：超过官方基线还没过关，基本就是没懂。

范围写死在代码里而非做成 flag：这样「扩大规模」是一次有 diff 的代码改动，
而不是谁顺手把参数调大。预算闸门要挡住的正是后者。

## D-009 模型在仓库**外**的中立目录里跑

**决策**：`bare_cc.call_model()` 用 `tempfile.mkdtemp()` 建一个系统临时目录作
子进程 cwd，并从子进程环境里删掉 `ARC_API_KEY`。

**理由**：Claude Code 会向上遍历父目录找 `CLAUDE.md`。若在仓库内启动，裸 CC 臂
会读到 `CLAUDE.md`、进而读到 `Theoria.md` 的全部设计、切堆清单、乃至这份
harness 本身。**读过理论的基线不是基线**——那一列的全部意义在于「零分工」，
被理论污染的话主表三列就没法归因了。

同理删掉 `ARC_API_KEY`：臂只应通过 harness 递给它的帧看世界，不应该有能力自己
去调 API（也顺带保证凭据不进入任何模型上下文）。

工具也一并关掉（`--max-turns 1`，无工具授予）：臂拿到帧、吐出一个动作，
仅此而已。给它 Bash 会变成在测另一个东西。

## D-010 prompt 走 stdin，不走 argv；且**不**清理 `ANTHROPIC_*` 别名变量

**决策**：`claude -p` 的 prompt 通过 stdin 传入；子进程环境保留
`ANTHROPIC_MODEL` 等陈旧别名变量不动。

**理由**：两个都是被真实故障逼出来的，都属于「静默走错模型」这一类最危险的
失败——不会报错，只会让数据变成假的。

1. **argv 里的多行 prompt 会让 `--model` 失效。** 一帧是 64 行 hex，
   经 Windows 的 `claude.cmd` shim 传参时被拆坏，`--model` 根本没送到 CLI，
   于是它回退到陈旧的 `ANTHROPIC_MODEL=Vendor2/Claude-4.6-Opus` 并 404。
   **单行 prompt 两种传法都正常**，所以这个 bug 一直藏到第一帧真实数据才暴露。
   实测：短 prompt/1KB/5KB 无换行全部正常，5KB 带换行必然失效，stdin 全部正常。
2. **清掉别名变量会让 CLI 的内部调用回退到另一个默认模型。** 第一版把
   `ANTHROPIC_*` 全删了，结果 CLI 用一个别的默认模型去跑内部调用，其安全分类器
   把 64×64 的 hex 墙判成可疑内容，整臂直接失败。`--model` 已经能覆盖别名，
   删它们没有收益，只有副作用。

教训与 `INC-003` 同源：**一个静默走错模型的 harness，比一个报错的 harness 危险得多。**
所以矩阵里每个 model id 在开跑前都单独实跑过一次（`AUDIT.md` §4.4）。

## D-011 方差包络：只跑 haiku 一档，每局重复 3 次，每次 30 个动作

**决策**：Phase 3 方差包络固定为 `claude-haiku-4-5-20251001` × 4 局 × **3 次重复**
× 每次 **30 个动作**；范围写死在 `run_campaign.py` 里，不做成 flag（同 D-008）。

**理由**：

1. **重复次数取 3**，是 `Theoria.md` Phase 3 经济「对照两臂各跑 ⟨2–3⟩ 局出方差包络」
   区间的上界。取上界是因为这批数字有一个下游用途：Phase 4 冻结清单里
   「每格重复数 ⟨n⟩ 由开发堆方差在冻结前定（方差小则 n=1 可辩护，否则 n=2）」。
   用 n=2 的样本去定 n 是循环论证——2 个点估不出方差的置信度。3 个点也不多，
   但它至少让「方差小」这句话有个能算的量。
2. **只跑 haiku 一档**：试点里它是唯一 4/4 可用的档（`BUDGET_REPORT.md` §2.1），
   每动作只要 opus 的 23%，且动作成功率最高（71.3%）。方差包络问的是
   「同一格重复跑，散布多大」，不是「哪档更强」——跨档比较试点已经买过了。
   多跑一档只会把 $12 变成 $47，买不到新问题的答案。
3. **每次 30 个动作**而不是试点的 20：20 步的样本里 `levels_completed` 全是 0，
   比率类指标（$/动作、HTTP/动作）在 20 步已经稳定，但**行为类**指标
   （状态重访率、无进展最长连击——Phase 2 电池的探索族）需要更长的轨迹才有分辨率。
   30 是「比率仍然稳、行为开始有形状」与「一格别超过半小时墙钟」的折中。

**代价与已知偏差**：包络是 haiku 档的，不能外推到 opus 档；Phase 4 若换档，
⟨n⟩ 需重测。这条写在 `BUDGET_REPORT.md` §10。

## D-012 闸门是一个**落盘**的对象，不是进程里的一个计数器

**决策**：`run_campaign.evaluate_gate()` 只从 `out/campaign_cells.jsonl`
（append-only 的逐格记录）计算，结果写 `out/campaign_gate.json`；
每局开跑**之前**先评一次（红则不开跑），跑完再评一次。

**理由**：一个只存在于「正在花钱的那个进程」内部的闸门不是闸门——进程一崩、
或者换一个进程接着跑，闸门就归零了，而钱是累计的。落盘之后，
「已经花了多少」这个问题任何时候都有一个不依赖进程存活的答案。

`INC-BA-003` 把这条的不足也暴露了：落盘还不够，闸门还必须是**跨会话共享**的。
本轨道当前两套战役各算各的总账，谁都看不见合计数。修法（共享闸门文件由所有
战役进程共同累计）已作为建议记入 `INCIDENTS.md`，本会话不代对方会话实施。

## D-013 上游 Schema 轨迹：载荷 gitignore，清单与哈希入库

**决策**：路 A 拉下来的 4 局轨迹落在 `schema_traces/`，**载荷不进 git**；
`schema_traces/MANIFEST.json`（来源、revision、逐文件 sha256、拒绝计数）**进 git**。

**理由**：两条，方向相反但结论一致。

1. **许可证**：上游数据集**未声明任何许可证**（`SCHEMA_LOCATE.md` §2.3）。
   `Theoria.md` Phase 4 的释出清单会公开全部 tracked 文件——把一份没有许可证的
   第三方数据 commit 进来，等于替它决定了可再分发性。清单与哈希不涉及再分发，
   却足以让任何人复现同一份材料并逐字节核对。
2. **可复现性**：账本要的是「我们用的是哪一份材料」，那是 revision sha
   加逐文件 sha256，不是那几十 MB 本身。

**代价**：`schema_traces/` 在别的机器上要重跑一次 `fetch_schema_traces` 才有。
`MANIFEST.json` 里的 `payload_sha256` 让「重跑拿到的是不是同一份」可判定。

## D-014 下载守卫是**正向白名单**，且先于任何内容请求

**决策**：`fetch_schema_traces.py` 只在**文件清单**（纯文件名）上做过滤，
判定为 `allow` 的必要条件是路径里含 4 个开发堆 game_id 之一；
封存判定**先于**开发判定；两者都不中的路径一律 `deny_unknown`。

**理由**：

1. **反向名单会开放失败**。「除非路径里有封存 id，否则下载」这种写法，
   遇到任何没预料到的路径形状（顶层汇总、压缩包、改过的目录命名）都会放行，
   而放行一次就不可撤销。正向白名单遇到没预料到的形状只会**少下**，
   少下可以补，多下不能撤。
2. **顶层聚合文件默认拒绝**，尽管它们看起来无害：
   `evaluation_results.csv` / `baseline_actions.csv` 含全部 25 局的逐局行，
   对其中 21 局就是 `piles.json` 的 `scores_only` 级污染。
   「看起来只是分数」正是 `piles.json` 把 `scores_only` 单列一档的原因。
3. **封存先判**，所以一个同时点名封存局与开发局的跨局文件会被拒绝而不是放行。
4. **过滤在清单上做，不在内容上做**。`INC-BA-001` 的教训逐字：
   「判断一个页面是否安全，需要先读它」——所以判定必须只用文件名，
   文件名是这套 artifacts 里唯一可以先看的东西。

**执行纪律配套**：跑下载的子代理被明令**不得**用浏览器/WebFetch/WebSearch 打开
该数据集，**不得**读取任何下载下来的文件内容（连开发堆的也不读），
主上下文只接收清单与哈希。下载不等于阅读——只要没有任何模型读过那些字节，
封存纪律就还在。

**首次执行即失败，且是朝安全方向失败**：上游路径只写 4 字符前缀
（`..._max_ar25_100.0`），从不写完整 pile id，而 allow 分支当时只测完整 id ——
于是 165 个本该下载的文件全被判成 `deny_unknown`，`allow` 为 0，一个字节都没下。
子代理照令**停下并报告**，没有自行放宽白名单。这正是 D-014 想要的失败方向：
「少下可以补，多下不能撤」。修法是让 allow 分支与 sealed 分支共用同一个
边界锚定的前缀正则（`names_game()`），且 sealed 仍先判。
配套补上 `tests/test_whitelist.py`：19 个用例，覆盖全部 21 个封存 id × 3 种路径模板、
「前缀落在哈希中间」、「一条路径同时点名两堆」三类。

## D-015 scorecard 的关闭必须重试——那是分数唯一一次可取的时刻

**决策**：`arc_client.close_scorecard()` 对 404 线性退避重试（默认 8 次），
与 D-005 对 gameplay 400 的处置同构；耗尽后写一条
`scorecard_close_failed` 到 `probe_log.jsonl`，写明后果。

**理由**：`Theoria.md` Phase 1 的对账义务是
「账本推得的分数必须等于 API scorecard 分数，不等 = incident」。
本轨道此前**无法履行**这条义务，原因不是没想到，是一个静默的失败：

* M4 试点的 23 次 scorecard 关闭里，**22 次返回 `404 scorecard <id> not found`**，
  且 `close_scorecard` 当时不重试、`raise_on_error=False`，于是全部静默丢弃。
* 关掉的卡**取不回来**：实测 `GET /api/scorecard/<id>` 与再关一次，
  各重试 8 次，全部 404。**分数只在关闭成功的那一次响应里存在，错过即永久丢失。**
* 结果是 14 个试点格里只有 1 个可对账。

那一个可对账的格子顺带回答了 `BUDGET_REPORT.md` §4 悬了很久的问题：

| | 值 |
|---|---|
| harness 记的成功动作 | 14 |
| harness 记的失败动作 | 6 |
| scorecard `total_actions` | **14** |

**scorecard 只计成功动作，失败的 400 不计。** 这是 §4「乐观口径」的直接证据，
9.7 倍不确定性里偏乐观的那一端。**但一个样本不是结论**，且 scorecard 计数
未必等同于配额计数（两者可以是不同的账）。本次战役修好重试后，
games 2–4 的 9 个格会各给一个数据点；ar25 那 3 个格开跑于修复之前，
其对账数据大概率已丢失，如实登记为缺口，不回填。

**为什么改的是共享文件**：`arc_client.py` 与另一场在飞行中的战役共用。
Python 在进程启动时就把模块载入了，因此**对方正在跑的四个进程不受影响**；
新进程拿到的是一个严格更好的关闭路径。改动是纯增量的——
原本就是 `raise_on_error=False`，不改变任何调用方的语义。

## D-016 中止阈值拆成两条，因为原来那一条量的不是它声称的东西

**决策**：`bare_cc.play()` 的 `actions_failed >= 10` 换成两条规则，
**两个不同的结局名**：

| 规则 | 阈值 | 结局 | 它主张什么 |
|---|---|---|---|
| 连续失败 | `CONSECUTIVE_FAILURE_ABORT = 10` | `api_unusable` | API 不可用 |
| 累计失败 | `cumulative_failure_cap(budget) = max(10, budget)` | `failure_grind` | 这条臂失败率高 |

**理由**：`BUDGET_REPORT.md` §11.2 已经把病因写清了——三个 ar25 格全部
`api_unusable`、失败动作数**全是 10、标准差 0**，因为 30 动作预算 × 约 0.6 成功率
的期望失败数约 12，必然先撞上一个绝对的 10。**那个判定是由构造保证的，不是 API 挣来的。**
试点从没撞到，只因为它的预算是 20、成功率 0.713，失败落在 5–7。

同一份文档的 §7 曾把这条规则描述成「**连续** 10 次动作失败即中止」。
那句话说错了代码——**而它说对了规则应该是什么**。「API 不可用」是关于失败
接连到来的主张；散落在一整局里的失败是关于**臂**的主张，把两者合成一个结局名，
正是那三个 ar25 格读不出信息的原因。

**§11.3 立的规矩是「阈值要改，但不能是为了过闸门而改」，逐条对照**：

* 那三个格真正测到的劣化——成功率 0.595、http/动作 9.66、$/动作 +68%——
  分别由 **G5、G3、G2** 测量，三条**一字未动，全部仍在武装状态**。没有信号被静音。
* 被删掉的是一个**不随它所判量缩放**的绝对常数。
* 被加上的是一条**原先不存在**的约束：累计计数器永远不会被成功动作清零，
  所以此前**没有任何东西在看失败是否连成一串**。
* `failure_grind` **不进** `DEAD_OUTCOMES`。一个花完预算、失败很多的格是**结果**，
  把它记成 API 故障，等于把一次真实测量扔进 G4 的死格连击里，
  然后因为「测到了东西」而停掉战役。
* 逐格仍然记录 `actions_failed` 与新增的 `actions_failed_consecutive_max`
  （失败是成串的还是散落的——旧的累计计数器对它杀掉的任何一格都答不出这个问题）。

**为什么现在能改**：§11.5 第 2 条把它挂起的理由是「改 `bare_cc.py` 会影响另一场
在飞行中的战役」。那场战役（`harness.campaign` 的四个进程）已经不在了，进程表已核。

## D-017 本轨道的出网路径接进共享闸门，因为它此前根本不在任何闸门上

**决策**：新增 `harness/spend.py`；`ArcClient.request()` 没有 `spend_binding`
就**拒绝开 socket**；`bare_cc.play()` 没有它就拒绝开跑；
每次 ARC HTTP 请求记 1 个 action，每次 `claude -p` 调用先按上限预授权、
返回后按 CLI 自报的 `total_cost_usd` 结算。逐格一个 reservation。

**理由**：`proxy/spend_gate.py` 已经落地，但它挂在**代理的出网路径**上，
而 `baseline-arms` 两条路径都不走代理——`bare_cc` 直接用 `arc_client` 打
`three.arcprize.org`，模型侧是 `claude -p` 子进程。所以接线之前，
共享账本对本轨道跑过的**每一场**战役都显示 `$0.0000`。
**那不是一个小数字，那是没有数字。** INC-BA-003 的代价正是「没有任何一方的
计数器看得见合计数」。

三个具体口径，各有理由：

1. **按请求计费，不按成功动作。** `spend_policy.json` 的 `action_ceiling` 自带的
   provenance 就写明它**不是** scorecard 的成功动作数。按请求记，D-005 的 5–11×
   重试放大对池子**可见**，而不是藏在它后面。
2. **失败的请求照记。** 一个 400 已经过了线、已经计入速率限制、已经发生了。
   只为成功计费的池子，正好按那个放大倍数低估自己。
3. **逐格一个 reservation，不是逐场战役一个。** 三次重复是并发跑的，
   共用一个 claim 会让三个线程共用一套计数器，于是**没有任何一格说得出自己花了多少**——
   那正是 INC-BA-003 第三条损害（一个 append-only 文件混了两场战役、没有一行能说清
   哪行属于哪场）在低一层的重演。

**顺带修的一处**：`load_api_key()` 原先只在导入方的 checkout 里找 `.env`，
而 CLAUDE.md 要求所有 agent 在 `.worktrees/<id>/` 里工作，那里没有这个文件
（它是 gitignored 的，不随分支走）。改为 worktree 回落到主 checkout，
与 `spend_gate.py` 解析池账本路径的做法同构、理由相同。密钥仍然只从
gitignored 文件读，一份都没有被复制到别处。

## D-018 闸门需要一个「已裁决」的记录，否则它只能停一次

**决策**：新增 append-only 的 `out/campaign_barriers.jsonl`。一条 barrier 记录
「哪些格已被裁决、由谁、修了什么」，并**只**移动**状态时钟**：G4（连续死格）
与 G6a（首格开跑至今的真实经过时间）。**累计量一律不动**：
G1 / G1b / G2 / G3 / G5 / G6b / G7 继续对**有史以来每一格**求和。

**理由**：预算闸门是一个「停下来裁决」的机制，但第一版没有任何地方能记下
裁决已经发生——于是 G4 一旦触发就是永久的，`BUDGET_REPORT.md` §11.5 那句
「复跑直接追加，`--gate-only` 随时可重新裁决」实际上**到不了**。

八条阈值分两类，这条界线写在这里，免得被一条一条地发现：

* **状态时钟**（G4、G6a）：各自主张「现在正在发生什么」——「API 在反复失败」、
  「这东西跑了一整天」。一场跑了 24 分钟、在一次正确的拒绝上停下、被诊断、
  16 小时后恢复的战役，既没有活着的失败连击，也没有一整天的运行——
  它有的是一个**间隔**，而把间隔计进去是与「G6 拆成两条」同一族的量纲错误。
* **累计和**（其余六条 + G7）：花掉的钱不予豁免，烧掉的计算时照算，
  封存堆接触不是裁决能退休的东西。

**防的是什么**：一条重置了美元合计的 barrier 就是 §11.3 禁掉的那一手。
所以判据写成测试而不是写成承诺——`test_a_barrier_moves_g4_and_nothing_else`
里那条**否定断言**（`cost_usd` 前后相等）才是承重的，
只断言「闸门变绿了」的测试对那个被禁的改动同样会通过。
另外 `remediations` 是必填的，空的直接拒收：裁决与静音的全部区别，
就在于有没有东西真的被改了。

**BAR-001 明确没有做的事**：ar25 那三个格不复跑、不删除、不改判，
degraded 标注照留，$2.5275 照算。

## D-019 战役中途换了传输层，而文档里写着不会换

**决策**：cookie jar **保持开启**（`ArcClient(cookies=True)`，现有默认值），
并把 `arc_client.py` 里那段声称「保持 `cookies=False`」的文字改掉——
**它从来没有对应过代码**。同时明确登记：`BUDGET_REPORT.md` §2.1 的单价与
§3 建立在其上的全部外推，是在一个**已经不存在的传输层**上测得的。

**这是怎么发现的**：不是被 harness 发现的，harness 里没有任何东西会发现它。
是 g50t 三格跑完后的一次对抗性审计——它被要求去**证伪**「30 成功 / 0 失败」
这个好得可疑的结果，于是去找「失败被静默吞掉」的机制。没找到吞掉的路径
（`resilient()`、动作循环、`request()` 三处都如实记账），却找出了真正的原因。

**证据，来自本轨道自己的 probe log**：

| 传输层 | HTTP 调用 | 200 | 400 | 404 | 500 | 传输错误 |
|---|---|---|---|---|---|---|
| jar **关**（M4 试点 + ar25 包络，全部历史） | 1922 | 249 | 1315 | 147 | 208 | 3 |
| jar **开**（g50t，本战役） | 99 | **99** | 0 | 0 | 0 | 0 |

`arc_client.py` 的模块文档此前写着：「本轨道自己的数字是在无 jar 的传输层上测的，
所以保持 `cookies=False`：一件你没法还原的仪器就是一件你没法复验的仪器，
`BUDGET_REPORT` 的数字应当被重新测得，而不是被悄悄重新解释。」
**意图是对的，而它对代码的描述是错的**——jar 落地那次提交（`e2915e1`,
2026-07-28 10:24 +0800）就把 `__init__` 的默认值设成了 `cookies=True`，
除 `transport_ab` 外没有任何调用方传别的值。于是 `bare_cc`、连同整场方差战役，
**无声地换了传输层**，而那段文字仍在声称它没换。

**后果，分开说清楚**：

1. **ar25 三格与 g50t 三格之间隔着两个变量**，不是一个：并发争用（INC-BA-003）
   *和* 传输层。两者不可分离。这加强而不是削弱了把 ar25 排除在包络之外的理由——
   它现在是双重不可比，而不是单重。
2. **包络本身不受影响**：g50t / sk48 / tn36 九格全部在 jar 开启下测得，
   彼此一致，而包络问的是「同一格重复跑散布多大」，那是格**内**的量。
3. **`http_per_action` 不再是 7.11，在 jar 上是 1.0。** §3 那些外推
   （$1,047–$2,094、8.8 万–17.5 万次 HTTP）的 HTTP 乘数因此高了约 7 倍。
   钱的部分不同步下降——模型侧计价与传输无关——但**动作配额**那一半的估计
   要重做。这条不由本工单裁决，如实登记。

**为什么不关掉 jar 去对齐历史**：那会让 g50t 与 sk48/tn36 互不可比，
而「同一格的重复之间可比」正是方差包络唯一不能牺牲的性质。
jar 是一个 arc-recon 实测过的真修复（20/20 对 0/20），不是一个可选项。

**顺带修的一处，同样来自那次审计**：`spend.py` 的 `usd_charged` 每步
`round(..., 6)` 累加，于是与同一批数字的直接求和最多差 $0.000006。
钱上无关紧要，作为主张则要紧——「池子与格子完全一致」这句话必须经得起
逐位核对。改为原样累加、只在输出端取整。
