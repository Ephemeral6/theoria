## 0. 一句话结论

**（2026-07-28 重算，用 §13 的实测单价；旧数字见本节末）**

**跑满「全部开发堆 × 三个模型档位」的裸 CC 基线是
$1,112 – $2,223、2.9 万 – 5.8 万次 HTTP 调用、四路并行 25 – 49 小时墙钟。
Schema 复现那一半是 $0——因为它根本跑不了，官方 harness 代码从未发布。**

已经花掉的：试点 **$9.84**、方差包络 **$10.54**、§2.1 重测 **$19.83**、
`$/调用` 复测 **$1.36**，合计 **$41.57**。

**上面那个区间是下界。** §14 查明 `$/模型调用` 的上涨不会回落——它来自
`claude -p` 包装层自己的缓存前缀，不是计价变动、不是传输层、也不是本 harness
的 prompt——且最新一格比 §13.1 的均值再高 16%。**批预算时按 +15–20% 留余量。**

**旧结论（按试点单价，D-019 之前）**：$1,047 – $2,094、8.8 万 – 17.5 万次 HTTP、
并行 45 – 89 小时。**钱基本没变，HTTP 少了三分之二，墙钟少了一半**——
差别不是省了钱，是省了时间和配额，见 §3.5。

| 口径 | S1 | S2 |
|---|---|---|
| 乐观（只有成功动作计费） | 9,042 动作 | 18,084 动作 |
| 悲观（每次 HTTP 尝试都计费） | 87,527 动作 | 175,053 动作 |

> **（2026-07-28 重算，jar 开）** 悲观口径降到 **S1 28,754 / S2 57,507**，
> 乐观口径不变（它不含重试）。**9.7 倍收窄到 3.2 倍。** 下面那句「批准全量之前
> 应当先问清配额口径」已不再是阻塞项：§4.1 的证据把悲观口径本身也否掉了，
> 而即便按它算，28,754 也在一个数量级之内。

**两者差 9.7 倍。** 这个不确定性来自 `DECISIONS.md` D-005 的重试策略——
平均 7–11 次 HTTP 换 1 个成功动作。**批准全量之前应当先问清 ARC 侧的配额口径**，
否则可能在毫无预警的情况下烧穿配额。

### 4.1 更新（2026-07-28）：**重试放大不吃配额**，4/4 实测一致

不必去问了——账里本来就有答案，只是此前没人对过。scorecard 的
`total_actions` 与账本的成功/失败动作数逐格比对，**4 个独立样本全部一致**：

| 来源 | 账本成功动作 | 账本失败动作 | scorecard `total_actions` | 分数来源 |
|---|---|---|---|---|
| M4 试点 g50t × opus | 14 | 6 | **14** | 关闭响应 200 |
| 包络 ar25 rep1 | 11 | 10 | **11** | 关闭响应 200 |
| 包络 ar25 rep2 | 14 | 10 | **14** | 开卡快照（episode 结束后 3 次，恒 14） |
| 包络 ar25 rep3 | 19 | 10 | **19** | 开卡快照（终局前 21 秒，9/10 次失败已发生） |

**scorecard 记的恒等于成功动作数，一次也不等于「成功 + 失败」。**
四格分属两个模型档、两个游戏、两次战役。

> **（2026-07-28 更新）样本从 4 增至 19**：方差包络九格（§12）与 §2.1 重测
> 六格（§13）全部对上，无一例外。三个模型档、四局、三场战役。
> 下面「样本量 4，全部来自同一时期、同一套 harness」那条限定**已经过时**，
> 但仍保留原文，因为它当时是对的——第 3 条限定现在应读作：
> 样本 19，跨两种传输层与三个模型档，仍非文档确认。

**这条结论到底回答了 §4 的哪个问题——必须说准，否则会被用过头：**

§4 的悲观口径是「**每次 HTTP 尝试都计费**」，它的来源是 D-005 的重试策略——
平均 5–11 次 HTTP 换 1 个成功动作。**被否掉的正是这一条**：那 30 次失败动作
背后是 8 次 HTTP 重试各自的 400/500，而 scorecard 一次都没记。
所以 **D-005 的 5–11× 放大不转化为配额消耗**，§4 表里那个 9.7 倍的上界不成立。

**它没有回答、也不该被说成回答了的**：

1. 那 30 次失败全是 **HTTP 400/500——服务器在执行之前就拒绝或出错的请求**。
   本条是「被拒绝的请求不计费」的证据，**不是**「语义上白费的动作不计费」的证据。
   一次打在空处的点击、一次无效果的按键会返回 200，照样进 `actions_ok`，
   照样计费。**别把这条写成「ARC 不为失败动作计费」。**
2. **scorecard 计数未必等于配额计数**，两者可以是两本账。这是目前能拿到的
   最强证据，不是文档确认。
3. 样本量 4，全部来自同一时期、同一套 harness。

即便如此，对 `INCIDENTS.md` INC-BA-003 里两场并发战役的配额风险，
这是一次实质下调：配额按成功动作走，而成功动作数是我们自己直接控制的量。

**取得这个证据本身差点没取成**，见 `DECISIONS.md` D-015：
关掉的 scorecard 取不回来，而试点 23 次关闭里 22 次 404 且不重试，
所以 14 个试点格只剩 1 格可对账。本轮补上重试，并对已在飞行中的 3 个
episode 用「快照仍打开的卡」抢救回 2 格——上表第 2、3 行就是抢救来的。

## 5. Schema 复现：$0，因为跑不了

**外推值：$0，动作配额 0。** 不是省下来的，是不存在。

官方 harness 代码**从未发布**（`schema-harness` GitHub 组织下只有项目主页仓库本身，

`Theoria.md:271` 的 `⟨复现值⟩` 保持空白。完整定位结果见
[`SCHEMA_LOCATE.md`](SCHEMA_LOCATE.md)。

闸门之后若要补这块，唯一低成本合规路径是**路 A**：上游把轨迹 artifacts 公开了
（HF，逐局分目录），按目录名**精确只取开发堆 4 局**。成本 ≈ $0、动作配额 0。
`Theoria.md:311` 已明确许可这种用法。

⚠ 但这件事有一个必须先解决的风险：该数据集**覆盖全部 25 局**，整包拉取
= 21 局封存游戏全部污染，且其内容（成品 world_model 源码 + 作者笔记）
比玩那一局更具破坏性。M3 检索过程中已经因此发生了一次污染事故

**任何下载都必须先有一个只允许 4 个 game_id 前缀的守卫**，写法与
`arc_client.assert_playable()` 同构。

### 11.2 触发原因：一个真实的劣化，加一个阈值假象，必须分开说

**失败动作数三格全是 10，标准差 0。** 这不是巧合，是
`bare_cc.play()` 的中止规则：`actions_failed >= 10` 即判 `api_unusable`。
**它是累计计数，不是连续计数**——§7 当时写作「连续 10 次动作失败即中止」，
**那句话是错的**，此处更正。

于是有一个纯算术的后果：动作成功率约 0.6 时，30 个动作预算下**期望失败约 12 次**，
必然先撞上 10 这个绝对阈值。**在这个预算与这个成功率下，`api_unusable` 是由构造
几乎注定的**，它不完全是「API 不可用」的证据。试点用 20 的预算、成功率 0.713，
失败落在 5–7，所以从没撞到过——这个交互一直藏到预算提到 30 才暴露。

但劣化本身也是**真的**，对照试点单价（§2.1，同为 haiku 档）：

| 量 | M4 试点 | 本次 | 变化 |
|---|---|---|---|
| 动作成功率 | 0.713 | **0.595** | −16.6% |
| HTTP / 成功动作 | 7.11 | **9.66** | +36% |
| $ / 成功动作 | $0.0342 | **$0.0574** | **+68%** |

三项同向劣化，与 `INCIDENTS.md` INC-BA-003 预测的后果一致：
本会话 3 个 episode + 对方战役 2–4 个进程 + `arc-recon` 的 `precheck.py`，
三套负载同时压同一个 API。**§10 写下的「已知偏差」在第一局就兑现了。**

**结论要分两句说，不能合成一句**：G4 停得对——在这种条件下继续跑，
买到的是争用的方差，不是臂的方差；但 G4 的**近因**是一个不随预算缩放的绝对阈值，
**远因**才是并发劣化。两者都要修，且修法不同。

### 11.3 明确记下**没有**做的事

**没有把 `actions_failed >= 10` 调大再跑一遍。** 这是本轮最该防住的动作：
它能让闸门变绿、让战役跑完、让报告好看，而代价是把一个真实信号调成静音。
`DECISIONS.md` D-008 把范围写死在代码里而不做成 flag，防的就是这一手；
工单也写明「预算闸门优先于任何『再跑一局』的冲动」。
**阈值要改，但必须是一次有 diff、有理由、在闸门之外被审过的改动，不是为了过闸门而改。**

## 14. `$/调用` 悬项：查清了（2026-07-28，$1.36）

§13.2 把 `$/模型调用` 上涨 53–68% 记为「成因未确定」，§6 建议 6 说值得花约 $2
去问一个问题：**它会回落吗？** 答案是不会，而且顺带查出了为什么。

### 14.1 复测：预测先写下来，再花钱

同局（g50t）、同档（haiku-4.5）、同预算（30）、jar 开，与包络三格只差 3 小时。
**开跑前先把三个分支写死**，免得事后挑一个顺眼的解释：

| 分支 | 判据 |
|---|---|
| 涨幅仍在 | $/调用 落在包络三格的 0.0371 ± 3sd = **[0.0330, 0.0413]** |
| 涨幅回落 | 接近试点的 **0.0225** |
| 含混 | 落在两者中间，约 0.0298 |

**实测 $/调用 = 0.0453**，格子形态与包络三格一模一样
（30 成功 / 0 失败 / 30 次调用，$1.3595，1458 s）。

**结果落在预设的三个分支之外，而且是在高的那一侧**——比包络均值高
**6 个标准差**。这一条照实登记：预设的分支集合不完备，遗漏了「涨幅还在继续涨」。

同局同档的时间序列：

| 时间 | 战役 | $/调用 | 输出 tok/调用 |
|---|---|---|---|
| 07-27 17:01 | M4 试点（jar 关） | 0.0225 | 1,650 |
| 07-28 12:22 | 方差包络 | 0.0356 / 0.0376 / 0.0382 | 1,951 / 2,364 / 2,495 |
| 07-28 15:20 | 本次复测 | **0.0453** | **3,910** |

### 14.2 成因：是 `claude -p` 包装层的开销，不是我们的

四条证据，合起来只剩一个解释：

1. **单价没变。** 对 17 个 haiku 格做最小二乘，从四类 token 反解每 token 单价：
   **输出 = $5.00/Mtok，R² = 0.99998**，最大残差 $0.0033（格均成本 $0.96）。
   那正是 Haiku 4.5 的公开输出价。**成本完全由 token 数解释，计价没有动过。**
2. **我们送出的 prompt 没变大。** 账本逐条记了 `prompt_chars`：
   haiku 5,461 → 5,563（**+1.9%**），opus 5,468 → 5,699，sonnet 5,303 → 5,520。
3. **但计费的输入 token 大涨。** cache-write/调用：
   haiku 8,175 → 10,356（**+27%**）、opus 6,700 → 10,178（**+52%**）、
   sonnet 6,219 → 12,743（**+105%**）。**三档同向，且与传输层无关。**
4. **多出来的 token 不可能来自我们的 prompt。** 5,500 字符约 1,500 token，
   而 cache-write 是 10,000 以上。**差额来自 `claude -p` 自己的系统提示与工具定义**
   ——那是 CLI 的缓存前缀，本 harness 既看不见也管不着。

**输出 token 那一半是另一回事，且只影响话痨档**：haiku 1,831 → 2,760（+51%）、
sonnet 873 → 1,582（+81%），而 **opus 是 9 → 10，基本不动**。
所以 opus 那 +53% **几乎全部**来自第 3 条的 CLI 前缀，与它的回话长度无关。

**这条推断的限度**：看不到 CLI 的系统提示本身，所以「差额来自 CLI 前缀」
是**排除法得到的推断**，不是直接观测。能直接观测的是：价没变、我们的 prompt 没变、
计费 token 变多了。

### 14.3 结论与后果

* **不会回落。** 它不是瞬时状态，是包装层的一次版本级变化。按新常态计。
* **§3.5 的钱数是下界，不是高估。** 那些数用的是 10 格 jar-on 的均值 $0.0392；
  最新一格 $0.0453 高出 16%。**批预算时按 §3.5 +15–20% 留余量。**
* **§13.2「成因未确定」到此关闭**，替换为本节。此前否掉的两个候选
  （回合长度、游戏推进冲掉 cache）**仍然是被否掉的**——真正的原因是第三个，
  当时没想到去看 `prompt_chars` 与 cache-write 的**背离**。
* **对 Theoria 臂同样成立。** 这是 `claude -p` 的开销，任何走该 CLI 的臂都要付，
  三臂对比因此不受偏袒——但每臂的绝对成本都要按上调后的口径重算。

### 15.2 三件必须分开说的事

**一、`actions_failed >= 10` 这个绝对阈值又来了。** 两个跑起来的格子失败动作
数**都恰好是 10**——和 ar25 三格一模一样的指纹（§11.2）。成功率 0.5745、
预算 30，期望失败约 12.8，撞上 10 仍然是**由构造几乎注定**的。
§11.5 第 2 条（阈值应随预算缩放）**至今未修，本轮也没有修**——
P-12 要求「按原协议续跑」，改中止阈值就不是原协议了，而且那正是 §11.3 拒绝的动作。

**二、rep 3 是一种新的死法，而且它不是「臂的方差」。**
`no_reset_window`：30 次 RESET 全部失败，一个动作没发出，$0。
tn36 本轮 RESET 实测 **63 次尝试 / 6 次 200 / 56 次 400 / 1 次传输层错误
——成功率 9.5%**。这一格的 0 不是「裸 CC 这次表现差」，是**它根本没拿到会话**。
把它计进「臂的方差」会把「API 不让开局」算成「臂不稳定」，
这与把争用算成方差是同一个范畴错误。后果直接可见：

| 口径 | 成功动作 cv |
|---|---|
| tn36 三格（含 rep 3 的结构性零） | **0.949** |
| tn36 两格（只算真正开起来的） | **0.367** |
| ar25 三格（P-7，同为顶格争用下） | 0.276 |

**0.949 那个数不该拿去定 Phase 4 的 ⟨n⟩。** 本轨道不自行删格
（`summarise_campaign` 照实把三格全算进去），但这一条必须写在数字旁边。

**三、对账义务这次 0/3 完成，比 P-7 更差。**
三格的 scorecard 关闭各重试 8 次，**24 次全部 404**。D-015 补的重试在这种
API 状态下不够用。ar25 三格当时是 1 格靠关闭响应、2 格靠开卡快照抢救；
本轮**没有快照产生器**（`scorecard_snapshot_open_card` 是 P-7 手工发的），
所以三格全部无法对账。`Theoria.md` Phase 1 的对账义务对这三格**未履行**，
如实登记，不回填。

### 15.4 复跑前应当先解决的（在 §11.5 两条之外新增）

1. **中止阈值仍未随预算缩放**（§11.5 第 2 条，原样成立）。两轮五个跑起来的
   格子里有四个失败动作数恰好是 10。**这条不修，第三次续跑大概率仍是 G4。**
2. **`no_reset_window` 不该与 `api_unusable` 同权计入方差**。前者是「没开成局」，
   后者是「开了局但打不动」。建议：`summarise_campaign` 对二者分列，
   `⟨n⟩` 的输入只取真正开起来的格子——但**这是个会改变结论的口径变更，
   应由监控裁决，本轨道不自行执行**。
3. **需要一个 scorecard 快照产生器**。关闭重试在 404 率高时不够，
   而快照是 P-7 唯一救回对账数据的手段，目前只存在于人工操作里。
