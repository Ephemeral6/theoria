# S27 · `credential_in_body` 的 2439 条，全部是同一条误报

RES-4，2026-07-29。零 API 计费（只读已有记录）、零封存堆接触。
**全程未打印、未落盘、未传出任何疑似凭据的值。**

## 结论（三句话）

1. **真泄漏 0 条。** 逐条比 sha256，无一命中活钥匙的摘要。
2. **2439 条 incident 的 `detail` 只有 1 个互不相同的值**（按 sha256 去重）——
   也就是说它们不是 2439 个独立发现，是**同一条判断被重复记了 2439 次**。
3. **成因已定位**：检测器的 UUID 分支匹配到的是代理自己放进请求体的
   `guid` / `card_id`。二者实测都是标准 36 字符 UUID，
   而每个 ACTION 请求体都带 `guid`——于是**每一个动作都会触发一次**。

## 证据

`proxy/tools/triage_credential_incidents.py`（本次新增）。它的设计要点是
**决定不靠肉眼**：每个命中片段只导出「命中了哪条启发式、长度、字符类别分布、
所在字段名、sha256」，原文一律不出模块；判定真伪靠
`sha256(片段) == sha256(活钥匙)`，两边都不需要把值显示出来。

实测（主 checkout + 全部 worktree，1033 个 `.jsonl`）：

| 量 | 值 |
|---|---|
| `credential_in_body` incident 记录 | **2439** |
| 其中 `detail` 的**互异**取值（sha256 去重） | **1** |
| `detail` 长度 | 恒 46 |
| `detail` 的字符形状签名 | `a aaa-aaaaaa aaaaaa aaaaaaaa aa a aaaaaaa aaaa`（纯小写词与空格）——**是一句人读的说明，不是被匹配的片段** |
| 触发路径 | `/api/cmd/ACTION3` 510、`ACTION4` 490、`ACTION1` 454、`ACTION2` 425、`ACTION5` 411 |
| 启发式在全语料上的命中 | 394,352（`long_alnum` 286,712 / `uuid` 107,640） |
| 其中落在已知良性 id 字段下 | 71,236（18.1%），`guid` 36,077、`card_id` 35,159 |
| **哈希命中活钥匙的片段** | **0** |

`guid` 与 `card_id` 实测均为标准 UUID（`^[0-9a-f]{8}-...-[0-9a-f]{12}$`）。

## 这不是新发现，是被记下来却没被计价的已知代价

`proxy/redact.py:258-262` 的注释自己写着：

> 「`card_id` 和 `guid` 也是 UUID，所以在这里匹配只会抬一条 incident，
> 永远不会重写账本」

也就是说**这个误报是设计时明知并接受的**——接受的理由（漏报的代价远大于误报）
现在依然成立。变化的是**量**：当误报累计到 2439 条、且全部是同一条，
它就从「便宜的保险」变成了**告警疲劳**，而这正是工单点名的那件事：
**误报会让人把这条告警关掉，而那正是真泄漏溜过去的方式。**

## 建议的收紧（本轮**未**实施，理由在下）

按工单第 3 条：真泄漏为零 → 收紧启发式。但**不要动 `looks_like_credential` 本身**
——它宁可误报的取向是对的，改它就是在往漏报方向调一个凭据护栏。

应该改的是**调用侧**：`env_proxy` 在抬 incident 之前，先排除
「命中片段恰好等于本次会话自己的 `guid` / `card_id`」的情形。
这个比较是**拿代理自己刚发出去的值去比**，因此不可能把一把真钥匙误判成良性——
它排除的是「我自己写进去的那个 id」，不是「长得像 id 的东西」。

**我没有在本会话实施它。** 这是凭据护栏的代码路径，而我这个会话的上下文已经很长；
在接近上下文墙的时候改一条「漏报即等于发布密钥」的判据，正是会制造出
我一整天在抓的那种事故。留给下一个会话，判据与理由都在上面写死了。

## 留给下一个人的两条

  若哪天这个脚本报出非零，**立刻按事故流程走，不要先修启发式**。

  报告里应引用测量时点，不要引用一个会漂的数。
